# GPT6 に会話判断を移した接続

2026-09-09。通常エディターのサーバー（8000）へ反映済み。エディターを開き直すと新しい接続を使う。

## 変更

- 音声入力は Realtime の文字起こしを使い、話者付きの会話原文と現在の対象・実行状態を GPT6 Astra の Responses API へ渡す。Realtime に制作条件や依頼書を作らせない。
- GPT6 が検索・小さな編集・質問・制作判断を行う。返答をストリームで受け、文ができた時点で既存の音声接続へ渡す。全文・全ツール処理が終わるまで読み上げを待たない。
- 長い仕事の入口を execute_work に統一。モデルに prepare/edit を選ばせない。会話原文はアプリが実行側へ添付し、短い補足だけを任意で受け取る。依頼の変更は進行中の同じ仕事へ届ける。
- 音声の割り込みは古い会話応答と未再生音声を取り消す。進行中の制作は止めない。明示的な制作停止は既存の停止ツールで扱う。
- 制作結果の説明も GPT6 が保存後の実データから作り、Realtime が読み上げる。completion_spoken に発声結果を記録。
- GPT6 の返答はサーバーに保存。ブラウザーの会話ログが届く前でも次の発言から読める。古い会話は read_conversation でページを遡れる。通常のプロジェクトチャットとの自動混合はしない。
- 制作担当へ、下書き検品→結果報告→応答終了→アプリの検証・本番保存という順序を明示。保存前の本番表示を探し続ける停滞を避ける。

## 確認したこと

関連自動テスト 43 件が合格。その後追加した、ブラウザーの監査ログ到着前にも返答を保持するテストを含む 7 件を再実行し合格。Python のコンパイルと JavaScript の構文確認も合格。

実ブラウザー、実 GPT6、実 Realtime を使った隔離テスト：

1. `reasoning-e2e-9751de71`：目的の記憶、字幕追加、字幕の文言だけ変更。字幕の開始・終了時刻が変わっていないことを実タイムラインで確認。
2. `reasoning-production-8bb6791b`：既存 B の取り込み中に追加字幕と音声質問。作業の保存自体は成功したが、保存手順について担当が調査を繰り返したため説明を修正。最初のテストの終了待ち条件は発声完了を厳密に確認できていなかったので、最終合格の根拠にはしない。
3. `reasoning-production-357ed968`：修正後に通しで再実行。ジョブ `053f6d09-b93e-4242-b326-c54c8f1355e4` が既存 B を全5.013秒・元音声付きで配置し、会話途中の追加指示を受領、末尾1秒に「確認用B」を追加して保存。別ジョブに分裂しなかった。

3 の音声質問は合成したテスト発話を Chromium のマイク入力へ流したもの。実際の VAD・文字起こし・会話処理を通した。質問は「作業は止めずに教えて。このテストでは、新しく動画を生成する必要はある？」。GPT6 は新規生成不要と答え、制作は継続。人間の声・多様な雑音・長時間会話の合格を意味しない。

同テストでは、文字起こし到着 02:39:54.666 UTC → 最初の返答音声 02:39:57.069 UTC、約2.4秒。この一例の実測で、全発話が同じ速さになるという意味ではない。初回制作依頼は文字送信から最初の音声まで約5.3秒、追加指示は約8.8秒だった。全テストは完了通知の再生まで121.94秒。会話開始の速さと制作全体の所要時間は別に扱う。

完了通知は 02:40:54.170 UTC に completion_spoken と音声文字起こしを記録。保存済みの B と字幕を伝えた。実行担当がネイティブ画面での再生を確認できていない点も通知に含んだ。テストはブラウザー上の会話画面で、ネイティブエディターの画面操作を実行担当が直接見たテストではない。

8000 の反映後、配信 JavaScript、音声セッション、GPT6 のストリーム応答を確認。最初のシェル経由の確認発話は PowerShell の入力エンコードで疑問符へ変わったため、UTF-8 指定で再実行し、指定した日本語の返答を確認した。
