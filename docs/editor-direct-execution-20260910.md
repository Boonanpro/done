# 会話中のGPT6による直接編集

## 構造

音声はRealtimeで文字起こしし、会話原文を読むGPT6が判断する構成を維持。既存素材の配置にも制作担当を起動していた経路を変更した。

- ローカル動画・画像・音声の取り込みを会話側へ公開。元ファイルは保持し、実測した尺・寸法・ストリーム情報を返す。
- batch_editの操作仕様を制作担当と同じ定義から取得。引数が空のobjectだったためAIが調べ直していた問題を解消。
- 字幕のx/y座標説明を実レンダラーに合わせて訂正。x=中央からの横移動、y=下端から上への位置、既定y=0.08。座標の誤解で字幕追加→位置修正を繰り返した実ログを確認。
- 複数操作、作成結果のID参照、最前面レーン、複数位置での分割を会話側でも実行できる。
- 各変更は下書きで検証してCAS保存。競合・選択外の編集・途中の失敗では反映しない。再生位置と既存の表示倍率は維持。
- 空の作品に最初のクリップが入った時だけタイムライン倍率を全尺に合わせる。後の変更では利用者の倍率を維持。
- 長い調査・生成・PC操作は従来の制作担当へ渡せる。道具の削減や有料モデルの強制、Qwenの使用はしていない。

## 実機試験

`scripts/test_editor_direct_native.py` は実ネイティブエディターを起動し、GPT6 Responses、Realtime音声、実タイムライン保存、実再生を通す。独立した使い捨て作品のみを編集する。

1. 既存Bを元音声付きで全尺配置。
2. 最後の1秒へ白い字幕を追加。
3. 「今足した文字だけ」で文言変更。映像と音声が同一であることを照合。
4. 実PCM音声「さっきの最後の文字を、もう少し大きくして」。
5. 実PCM音声で音量を半分へ。文字と映像を保持。
6. 実PCM音声で2秒位置を映像・音声とも分割。素材範囲・尺・再生順を保持。
7. 実ネイティブ画面をキャプチャし、再生位置が進むことを確認。制作担当ジョブは0件。

音声試験の発話はWindowsのHarukaで合成して実Realtime入力へ流す。人間の声、咳払い、自然な割り込みの評価とは別。音声時間を含む保存時間と、発話長を差し引いた時間を区別して記録する。

独立サーバー試験 room direct-native-6c1eb347 は6依頼すべて成功。テキスト保存9.17 / 2.80 / 4.41秒。音声は発話終了相当から9.33 / 7.12 / 10.98秒。合成後のネイティブ画面を実際に確認。再生位置0.76→1.77秒。通常接続での最終値は追記する。

先の約140秒テストは複数依頼・会話・検証・完了通知を含む全体時間であり、ここでの1依頼の保存時間と単純比較しない。既存Bの取り込み自体の比較では、旧経路で初回反映約42〜56秒に対し、直接経路は実測約6〜9秒となった。各試験の入力・接続方式は報告JSONに残す。

## 限界と残る評価

これは制作担当起動の待ち時間をなくし、会話から実編集に直結したことの実証。あらゆる参考動画から高品質な新作を完成できることの証明ではない。参考探し・方向性の提案・下書き品質・長い生成・自然な人間の会話は、それぞれ通し制作でも評価する。

再生位置が一度約1.8秒の観測中0に留まる例があった。音声処理のエラー記録を追加し、その後の実機試験で再生進行を確認したが、最初の停止の原因を確定したとは扱わない。
