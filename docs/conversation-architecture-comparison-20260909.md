# 会話判断を GPT6 に移す比較と GPT-Live-1 調査

2026-09-09。結論：原文を GPT6 に渡す方向は有望だが、全文完成後に読み上げる直列構成を、そのまま本番へ入れるべきではない。制作判断の一部は改善した一方、発話が遅く、prepare/edit の境界問題も残った。

## 比較方法

6 ケース × 2 方式 × 2 回、計 24 件。全件 API 応答正常終了。

- 現行：gpt-realtime-2.1、reasoning high、現行の指示とツール。実音声を生成。
- 原文方式：gpt-6-astra、reasoning high、Responses API へ話者付き会話原文を直接入力。既存ツールを利用し、save_brief を除去、会話側の制作判断指示を制作担当の指示へ置換。GPT6 が返答と操作を決定。全文完成後、別の Realtime 接続が文章を読み上げる。
- 検索・参考取得・表示・制作・停止は固定した模擬結果。実プロジェクトや外部サービスには操作しない。検索結果の URL は example.invalid。見本の品質、表示の実成功、実制作時間は評価していない。
- 入力は文字起こしテキスト。音声認識、発話区切り、同時発話、実際の割り込み、聞き心地の主観評価は未検証。
- 原文方式でも既存 delegate_edit は残しており、GPT6 が実行担当向けの依頼を書く。会話原文を読む判断主体の比較であり、単一の継続 GPT6 セッションが全制作ツールを直接操作する最終構成の検証ではない。
- 条件と実行順は開始時に固定。2 回目は方式順を反転、同時接続 2。

初回の接続確認では、出力オブジェクトの status を次回入力へ再送した際に 400 エラー。status を除去し、参考取得の模擬結果で source 引数を反映するよう修正した後、全件を v2 として実行し直した。初回データは別ディレクトリに残し、以下の集計には含めない。

## 内容の評価

| ケース | 現行 | GPT6 が原文を読む |
|---|---|---|
| 実際のサッカー制作発言 | 1 回は抽象演出・文字・記号中心の指示。もう 1 回は準備と構成案へ委譲 | 2 回とも edit。人物・競り合い・ゴール・歓喜を扱い、参考の密度や動きを翻案。自分の尺・演出案を「ユーザー指定の制約ではない」と区別 |
| 「人物なしとは決めていない、そちらで考えてまず見せて」 | 参考再提示や参考探しへ戻り、ユーザーへ好みを再質問。1 回は 6 回に分けて説明しながら検索・状態確認を往復 | 2 回とも人物を含めた店の見本を edit で依頼。人物の有無を聞き直さず、演出判断を引き受けた |
| 無料条件を撤回、Google Omni 直接、5 秒、1 ドルまで、Higgsfield 不可 | 2 回とも prepare。仕様案・見積もり・準備へ寄る | 最新予算と課金先を正しく保持、許可内なら再承認不要と扱う。ただし 2 回とも prepare。1 回は調査後 edit の二段階を明示、もう 1 回は prepare 内で生成してよい旨も書く。既存区分の扱いは未解決 |
| 会話で既に伝えた対象者を質問 | 2 回とも大意は正答、静かに飲む等の補足あり | 2 回とも既知の目的を直接回答。ツール不要 |
| 参考動画を二つ探して見せる、制作しない | 2 回とも提示ツールまで到達。1 回は委譲と状況確認を挟んでから自分でも検索 | 2 回とも検索→取得→提示の直接経路。制作は始めない |
| 制作を止めるが会話は続けたい | 2 回とも stop_production のみ | 2 回とも stop_production のみ |

人物のケースの「まず見せて」には参考提示という解釈余地もある。単純な正誤率ではなく、ユーザーが期待する試作への進行との差として評価した。これだけで汎用的なモデル優劣や本番成功率は推定できない。モデルだけでなく指示・保存ツールも変えている。

## 時間（各条件 2 回の中央値、秒）

| ケース | 現行・初音声 | GPT6原文・初音声 | 現行・対象操作 | GPT6原文・対象操作 |
|---|---:|---:|---:|---:|
| サッカー制作 | 1.0 | 29.2 | 委譲 8.1 | 委譲 24.1 |
| 人物の扱いを訂正 | 1.1 | 32.6 | 制作委譲なし（参考調査への委譲は1回） | 制作委譲 25.9 |
| 予算変更 | 1.0 | 25.7 | prepare 委譲 5.7 | prepare 委譲 17.7 |
| 既知の目的に答える | 1.2 | 4.7 | — | — |
| 参考検索・提示 | 1.0 | 18.3 | 提示 10.4 | 提示 12.8 |
| 制作停止 | 0.9 | 7.9 | 停止 2.2 | 停止 1.8 |

現行の初音声は多くが相づちや着手予告であり、GPT6 側のツール実行後の最終返答と同じ意味の指標ではない。「約 1 秒で制作判断が完了した」とは読めない。

時計は入力準備後から。現行の Realtime 初期接続は除外。GPT6 側は最初の Responses リクエストから計時し、全文完成後の音声用新規接続も含む。常時接続や文章の逐次読み上げはまだ実装していないため、最適化後の性能比較ではない。

GPT6 側で観測された遅さには、既存ツールを使った複数往復、長い作業依頼文の生成、最後の返答生成、その後の音声接続が含まれる。各時間をすべて思考時間とは呼べない。ツール引数は response 完了時に受理したため、最速の逐次実行より遅い場合がある。

GPT6 側の読み上げ文字起こしは全 12 件で入力文章と完全一致した。ただし、これは音声自体の発音や自然さを人が評価した結果ではない。

## 次に採用すべき方向

1. 会話原文を GPT6 が読み、制作判断を担う経路を継続する。今回、人物や参考の扱いに改善が見られた。
2. GPT6 の全文・全処理完了後まで会話を止める構成は採用しない。会話と長い制作を独立して動かし、確定した返答を逐次音声へ渡す。相づちで実処理の遅さを隠すだけにはしない。
3. 今回は GPT6 が既存 delegate_edit に長文を書いている。会話側から作業系への二重の依頼書生成を減らし、原文・参照・状態を共通で読めるようにする。継続セッション、実行結果通知、必要時の直接操作を検証する。
4. prepare/edit の区分が、ユーザーに許可された一連の仕事を止めないようにする。料金確認は同じ仕事内の手順として扱い、調査結果後の継続までテストする。
5. 再生・停止と、既知の情報への返答まで毎回長い制作経路へ入れない。実際の音声入力と割り込みの検証は、その接続後に別途必要。

## GPT-Live-1 調査

OpenAI の公式紹介では、GPT-Live は同時に聞き話す方式で、検索・深い推論などを別の高性能モデルへ委譲し、その間も会話を続ける構成だと説明されている。今回目指す役割分離と近く、ユーザーが感じている自然な待ち方には、公開された構造上の根拠がある。

したがって、同等の能力をアプリへ組み込める API が提供されれば、会話の間合い・割り込み・裏の作業との両立の改善は期待できる。ただし、依頼の正確な伝達、編集対象の保持、素材や実行結果の連携まで自動で直るわけではない。委譲の内部形式や、アプリ独自ツールとの接続仕様は公開資料から確定できない。

2026-09-09 の確認では、公式に API 提供通知フォームがあり、開発者向け公開モデル一覧に gpt-live-1 は掲載されていなかった。このアカウントの models.list にもなく、models.retrieve('gpt-live-1') は 404 model_not_found。現環境で利用できる API としては確認できない。紹介記事の 7 月 31 日追記には API 経由の音声への言及もあるため、限定提供の有無まで否定せず、一般提供の接続仕様が確認できていないと扱う。
