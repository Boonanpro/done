各条件1回。モデルの選ぶ確認方法、起動・通信時間が異なるため、総時間差を修正の効果と断定しない。全体には接続・会話・音声生成・テスト待機が含まれ、各処理は重なる。ファイル観測はネイティブ画面への描画時刻ではない。completion_spokenは音声応答の生成完了であり、実スピーカーの再生完了を直接測ったものではない。

最後の条件は合成フレームと音声信号を確認したが通し視聴なし。先の条件の通し視聴と品質保証が等価ではない。テスト用会話ブラウザだけを開いていたため、制作担当はネイティブ画面を探してbrowserとコード調査へ進んだ。ヘッドレス試験の合格は実エディターでの操作合格ではない。

## 実装

- add_clip/add_caption/add_regionのlane="front"で実行時点の最前面に置ける。リンク音声の自動レーン追加で番号が変化しても推測不要。実API試験でもfrontを使い、一回のapply_editsで配置・字幕が反映された。
- apply_editsの引数に {"$result":0,"path":"clip_id"} を置けば先行操作の結果を参照。作成→追加編集をモデルへの往復なしで実行できる。配列も参照可。未来・不明な参照は全変更をロールバック。
- エディター制作担当の新規Codexスレッドは、同じsystem_promptをdeveloper設定と各ターンに二重搭載しない。各ターンの原文と現在の指示は維持し、一般チャットの設定・ツールは変更しない。既存スレッドは強制リセットしないため、既存の重複は通常のスレッド更新まで残る。
- 実ログの初回入力は71,735→53,734トークン（約25%減）。ただし最終試験は往復回数が増えており、総入力使用量の削減や応答高速化の保証ではない。
- scripts/analyze_editor_latency.pyで過去・今後のジョブログから区間を再計算。テストに保存時点を独立観測する処理も追加。

## ボトルネックの結論

この配置作業はGPU処理ではなく、編集操作約2秒に対し多数のモデル往復、重い入力、検証経路の探索が支配的。ツール外約69秒をすべて推論時間や無駄とは呼べない。既存イベントではモデル通信・キュー・内部推論を完全分離できない。

次の比較は実ネイティブ画面を接続し、同じ検証範囲で行う。制作担当が繰り返し読んだ仕様・状態と、実際に必要だった情報を照合して、情報取得の往復を減らす。使える道具を削ったり、未確認の結果を完了扱いして速さを演出しない。
