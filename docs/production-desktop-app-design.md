# 制作タブ デスクトップアプリ化 設計ドキュメント

決定（2026-06-27, ユーザー）：**制作タブ（動画編集）をデスクトップアプリ化**する。チャットは今のままWeb。
ダビンチ/プレミア級の「即時編集×安定×サクサク」を目指す。作った動画・編集状態は**共通DB/APIで繋ぎ**、
チャット側のDANもデスクトップで作った動画を認識できるようにする。ブラウザでこれ以上頑張らず、アプリ化で一気に改善。

このドキュメントは Codex 等の助言者と方針を揃えるための叩き台。

---

## 1. なぜアプリ化か（合意済みの前提）

- ダビンチ/プレミアは**デスクトップのみ**＝ブラウザでは即時×安定×大規模が構造的に出せない、という現実的サイン。
- ブラウザの構造的天井：丸ごとファイルDL（mmap不可）、タブのメモリ上限（334クリップ・6アセットでOOM）、
  デコーダ出力プールの制限、`<video>`/WebCodecsのライブ合成が重い。実測でこれらに当たり、パッチが収束しなかった。
- 「Electron/Tauriで包むだけ」では無意味。**メディア処理（デコード/合成/プレビュー/プロキシ/キャッシュ/書き出し）を
  webviewの外＝ネイティブに出す**ことが本質（ユーザー/助言者の意見と一致）。

---

## 2. アーキテクチャ

```
┌─ Web（今のまま） ────────┐      ┌─ Desktop App（新規・制作タブ） ──────────────┐
│ チャット / DAN          │      │  Shell: Tauri(Rust) ＋ WebView2             │
│  (Next.js, ブラウザ)    │      │   ├ UI: 既存の React 制作UIを再利用(webview) │
└──────────┬──────────────┘      │   │   (production-workspace / video-editor)  │
           │                     │   └ Native Media Engine（webviewの外）        │
           │                     │       ├ デコード(ハードウェア, 複数並列)       │
           │  共通 API/DB        │       ├ ライブ合成（多レイヤー・即時）         │
           ▼                     │       ├ フレームキャッシュ(RAM+ディスク, GB級) │
┌─ 共通バックエンド ──────────────┴───────┐ ├ プロキシ生成 / 書き出し(FFmpeg)        │
│ 既存 Python API + ストア                │ └ プレビュー出力(ネイティブ面)          │
│  /api/v1/production-assets/*            │                                        │
│  contents(タイムライン) / assets / jobs │←── Desktop も Web も**同じこのAPIを叩く** │
│  + Supabase / ファイルストア            │                                        │
└─────────────────────────────────────────┘                                        │
                                          └────────────────────────────────────────┘
```

**要点：Desktop App は“既存バックエンドAPIのもう一つのクライアント”**。
- タイムライン(contents)・素材(assets)・書き出し成果物は**今ある `/api/v1/production-assets` API＝共通DB**に読み書き。
- Desktop で書き出した動画は **generated asset としてこの共通DBに登録** → Web側のDANが従来通り認識できる（追加配線は最小）。
- DAN↔編集の連携（DANが「この動画にぼかし入れて」等）も、**同じ contents/annotations を介する**ので両側で一貫。

## 3. 再利用するもの / 新規に作るもの

| | 内容 |
|---|---|
| **再利用** | 既存 React 制作UI（タイムライン編集・素材パネル）／既存 Python バックエンドAPI＋DB（contents/assets/jobs）／サーバー側FFmpegレンダラー（最終書き出しの選択肢として） |
| **新規** | ① Desktop Shell（Tauri）② **ネイティブ・プレビューエンジン**（下記でエンジン選定）③ プレビュー面のwebviewへの統合 ④ React UI ⇄ ネイティブエンジンのブリッジ（load timeline / seek / play / 編集op を渡す） |

「足りないのは**ライブのプレビューエンジン**だけ」。プロキシ生成・書き出しは既にサーバーFFmpegで外に在る。

## 4. 未決：ネイティブエンジンの選定（PoCで白黒つける）

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **GES (GStreamer Editing Services)** ★暫定推奨 | NLE専用の既製ネイティブエンジン（タイムライン→即時プレビュー＋書出, Pitivi の中身, gstreamer-rs/ges bindings） | **再生・合成エンジンを自作しなくて済む**。レイヤー/トランジション/HWデコード対応 | GStreamerのビルド/同梱がOS別に面倒(~100MB+)。学習コスト |
| **FFmpeg/libav 直 + 自作エンジン** | libavで復号、自前で合成・同期・キャッシュ・再生器を構築（合成は wgpu 等） | 完全制御・配布が軽い | **ライブ多レイヤー再生エンジンを一から作る＝重い** |
| mpv/libmpv | 単体プレイヤー | 安定・容易 | タイムライン多レイヤー合成は守備範囲外（単体では不可） |

**暫定推奨＝GES**（車輪の再発明を避ける）。ただし一長一短。**PoCで実機検証して確定**する。

## 5. フェーズ（de-risk優先）

**Codexレビュー反映（2026-06-27）：Phase 0 は大きすぎたので、リスクの大きい順に PoC を3分割。
最も根本的な premise を最初に独立で潰す。3つ全部 green になって初めて MVP に入る。**

- **PoC‑1：エンジンの素性（唯一の生死判定・まずここだけ）**
  Tauri も webview も認証も無しの**スタンドアロンのネイティブ小プログラム**（GESを vehicle）で、代表的な
  多クリップ・タイムラインを **ハードウェアデコードで即時スクラブ・安定再生・OOM無し** にできるか、ユーザーPCで数字で検証。
  **ここがダメなら全部ダメ。** GESのWin/Macビルドが地獄なら、それ自体が早期の発見（配布リスクの予兆）。
- **PoC‑2：プレビュー面の webview 統合**
  ネイティブの絵を Tauri の UI プレビュー枠に重ねられるか（位置/リサイズ/重なり順の同期＝finicky な所）。
- **PoC‑3：編集の即時反映**
  カット/伸縮/移動を、プレビューが**待ち無し**で反映できるか（seek/差し替えの遅延）。
- → **PoC‑1〜3 全部 green** で初めて **MVP** へ。

- **MVP（PoC通過後）**
  既存 React タイムラインUIを Desktop に載せ、プレビューをネイティブエンジンに。基本編集が即時反映。
  書き出し→共通DBに generated asset 登録（DANが認識）。**§7の known-work（認証/素材/プロキシ/アップロード）をここで実装。**
- **フル**
  テロップ/PiP/ぼかし/エフェクトをネイティブプレビューに。DAN駆動機能。配布(署名/インストーラ/自動更新)。

## 6. プレビュー面のwebview統合（技術論点）

ネイティブの絵をどう画面に出すか（PoCで確認）：
1. **ネイティブ・オーバーレイ面**：エンジンの出力を専用面に描き、UIのプレビュー枠にピタリ重ねる。最高性能・ゼロコピー。短所＝リサイズ/スクロール/重なり順の同期。
2. **GPUテクスチャ共有**：Tauri/wgpu でテクスチャ合成。
3. **低遅延ストリーム**：エンジン出力をwebviewへ。実装は楽だが遅延。
推奨は①or②（本物のサクサク感）。

## 7. リスク（正直に）— premise-risk と known-work を分ける

**Codexレビュー反映：「足りないのはプレビューエンジンだけ」は楽観的だった。下記を明記。
ただし分類が重要——premise-risk（PoCで潰す＝生死）と known-work（難しいが解ける＝MVP工数）を分ける。
known-work で PoC を膨らませない（Codexの「PoCが大きすぎる」を実際に解消する）。**

### A. premise-risk（PoC‑1〜3 で白黒。ダメなら計画ごと見直し）
- ネイティブエンジンが多クリップを**即時×安定×OOM無し**で再生できるか（PoC‑1）。
- GStreamer/GES の Win/Mac **ビルド・実行**が成立するか（PoC‑1）。
- ネイティブ面と webview UI の**位置同期**（PoC‑2）。
- 編集の**即時反映**遅延（PoC‑3）。

### B. known-work（premiseを脅かさない＝MVPスコープ。実工数として計上）
- **認証**：デスクトップ用ログイン/トークン保存/更新（Web の cookie 認証とは別系統）。
- **ローカル素材管理**：ネイティブのファイルアクセス・取り込み・パス管理。
- **プロキシ**：サーバー側FFmpeg継続 or ローカル化（オフライン可否）の判断。
- **成果物アップロード**：ローカル書き出しを共通ストア/DBへ戻す（DANが認識する経路）。
- **配布/更新**：インストーラ・コード署名・自動更新（継続コスト）。
- ネイティブエンジンの独自バグの育成期間。

→ **PoC‑1（最小・生死判定）から着手。premise が証明されるまで B には手を付けない。**
