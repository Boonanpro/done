Galaxy S25、実際のDone部屋、Live 1で2026-09-18 05:21 JSTから確認。PCスピーカーで自然音声を入力し、端末画面・外部マイク録音・Androidログ・サーバーperf記録を保存した。

最初は端末が旧OTA `01a0b07e-8c07-76c1-a09b-d02f42dbf0b3` を使用していた。通話を終了して再起動し、更新 `01a0b0eb-24f5-7233-955b-aece22b2f2b7` の稼働をperfで確認。球体下の「確認中」とミュート時のアイコン・球体の変化を実画面で確認した。

3. 発話直後にホームへ戻す。相槌は聞こえるが結果は出ない。
4. アプリを前面に戻すと処理が進み、結果を自発的に回答。

## 実装原因と変更

`mobile/voice.tsx` はモデル応答のストリームだけ `expo/fetch` を使用し、検索・履歴・ジョブ取得・終了判定・記録はReact Nativeのglobal fetchを使用していた。

インストール済みソースでglobal fetchのwhatwg-fetch実装が応答のresolve/rejectを`setTimeout(..., 0)`へ送ることを確認。今回のNew ArchitectureではTimerManager.cpp→JavaTimerRegistry→JavaTimerManager.createTimerを通り、onHostPauseでタイマーフレームの実行が止まる。旧アーキテクチャのcreateAndMaybeCallTimerにある0ms即時実行とは別経路。

通話コンポーネント内の全fetchを既存のexpo/fetchへ統一。global fetch自体や他画面には変更しない。新しい常駐処理や発話プロンプトを足す必要はない。

global fetchが解決しない条件で、native通信による接続とバックグラウンドのジョブ完了通知が進む回帰試験を追加。mobile-live 22件、mobile型検査が通過。

ブラウザジョブの受付05:33:43.100→結果イベント05:34:18.214で35.1秒、完了状態の保存まで約37秒。端末の結果受信05:34:21.014→Live送信21.016→受付21.671→assistant発話イベント21.844。端末受信から発話イベントまで0.830秒で、すべてapp_state=background。サーバー時刻と端末時刻には約1秒の差があり、両者の時刻を直接引いてミリ秒単位の遅延を主張しない。発話イベントは音響的な発声時刻そのものではない。

再試験は固定の回答データを入れず、実APIと実ブラウザを使用。今回の背景通信停止は再現→変更→同条件での改善を確認できた。ブラウザ作業そのものはまだ35秒以上かかり、すべての遅延や過去の無言待機がこの一因だけだったとは主張しない。
