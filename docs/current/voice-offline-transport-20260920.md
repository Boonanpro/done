# スマホを外した状態での音声通信検証（2026-09-20）

## 範囲と現在の判定

実家で起きた音切れの解消はまだ実証していない。この記録は、スマホを抜いた後に実施した、無音・API呼び出しなしの検証。ChatGPTアプリとの悪回線下の同条件比較でもない。

`scripts/voice_transport_bench.py` を追加。ヘッドレスChromiumの2つのWebRTC接続の間に、ローカルUDP中継を置く。同じ録音を繰り返し送信し、欠落・遅延の揺れ・帯域制限を個別に注入する。Danのサーバー・会話履歴・認証・有料APIには触れない。通常ブラウザーも操作しない。

検証の成立条件:

- 送信側が選択したICE接続先が、中継のポートであることを確認。直結による回避を不合格にする。
- 接続先はこのPC自身のIPv4アドレスに限定。
- 音声サンプルと音声エネルギーの増加を確認。音声を復号していない試行を不合格にする。
- 入力WAVのSHA256、ブラウザー版、乱数種、通信条件、前後の統計を保存。
- 終了時にブラウザー・中継・送信予約を閉じる。

最初の試走は音声処理が動かず、サンプル数がゼロだったため無効。その後、外部への音はブラウザー全体のミュートで止め、内部の音声処理は動かすよう修正。有効な試行で置き換えた。

## 再現

```powershell
python scripts/voice_transport_bench.py --wav .tmp/voice-conversation-trial/audio_story.wav
python scripts/voice_transport_bench.py --wav .tmp/voice-conversation-trial/audio_story.wav --cases jitter,combined128,combined64 --bounded --nack-only --output .tmp/voice-transport-offline-bounded
python scripts/test_native_voice.py
node --test tests/mobile-voice-sdp.test.cjs tests/mobile-voice-quality.test.cjs tests/mobile-webrtc-field-trials.test.cjs
```

WAVは既存の試験用録音。第1コマンドは通常と再送ありの比較、第2コマンドは再送回数と再生待ち時間の調整候補をChromiumへ指定した比較。これはAndroidのネイティブSDKへの適用確認の代わりにはならない。

## 通常と再送だけの比較

数値は補完された音声サンプルの割合。人間が聞き取れる割合ではない。各条件1試行、固定の録音・乱数種。再送でパケット数が変わるため、失われるパケットが完全に同一という意味ではない。

|条件|再送なし|再送あり|再生待ち時間：なし → あり|
|---|---:|---:|---:|
|正常（8秒）|0.00%|0.00%|25 → 35ms|
|10%欠落（20秒）|2.50%|0.85%|32 → 56ms|
|片方向120±80ms（20秒）|0.99%|1.22%|128 → 125ms|
|片方向64kbps（20秒）|0.05%|0.13%|45 → 42ms|
|10%欠落＋120±80ms＋128kbps（20秒）|3.23%|3.44%|117 → 129ms|
|10%欠落＋120±80ms＋64kbps（20秒）|3.64%|4.15%|119 → 174ms|

欠落だけなら再送は有効だったが、順序の乱れ・制限を組み合わせると同じ改善にはならなかった。再送を有効にするだけでは完了にできない。数値の小さな差について有意差は主張しない。

証拠: `.tmp/voice-transport-offline/*.json`。

## 復元設定を分けた比較

Chromium 141.0.7390.37で、再送を各欠落につき一度に抑える設定と、遅着を学習する待ち時間設定を合わせて指定した。

|条件|再送だけ：補完割合／待ち時間|再送制限＋待ち時間調整：補完割合／待ち時間|
|---|---:|---:|
|遅延の揺れのみ|1.22%／125ms|1.05%／154ms|
|欠落＋遅延の揺れ＋128kbps|3.44%／129ms|2.48%／318ms|
|欠落＋遅延の揺れ＋64kbps|4.15%／174ms|2.48%／355ms|

補完割合は下がるが、待ち時間が増える。これをそのまま「音声体験の改善完了」と扱わない。証拠は `.tmp/voice-transport-offline-bounded/*.json`。ブラウザーへの指定値は結果JSONにも保存。Android SDK 144と同じ実装・効果だと断定しない。

続けて待ち時間設定を外し、再送回数制限だけを試した。128kbpsで4.30%／123ms、64kbpsで4.40%／146ms。今回の試行では、遅延を抑えると音声欠けの改善は残らなかった。証拠は `.tmp/voice-transport-offline-once/*.json`。この候補を採用済みの改善とはしない。

計17試行（通常＋再送12、待ち時間調整3、再送制限のみ2）。WebRTC受信統計を評価しており、音声認識・会話の正確性・主観的な聞き取り評価を17回通したという意味ではない。

## Atom用処理の確認

`DanExternalAudio` はスマホ経路ではマイクPCMを変更せず返す。Atom用待ち行列へ入れず、外部入力用の10ms待機も行わない。Javaの4組の検証で、スマホの通過、Atomの入出力、切替、古い接続の排除、キュー競合を確認した。これでAndroidの実際の音響処理性能を証明したわけではない。

スマホ単体の録音は `automatic`、Atomは `software` のAEC/NS指定。過去の実機比較ではプラットフォーム処理で入力の先頭欠けが改善したが、今回の受信音切れの全原因と同一視しない。

## 配布状態と残り

スマホを抜く前の診断用APKを、この作業では入れ替えていない。端末の通信障害プロファイルとADB中継は前段で削除済み。ソース側の一時診断フックも除去済みだが、新しい通常APKのインストールを済ませたという意味ではない。

再送・復元の候補は検証中。Core再起動なし。音を鳴らす試験なし。新たなAPI料金なし。

実環境での合格判定には、次が必要:

1. 候補設定を入れたAndroid実機で、同じ固定音声を入出力し、実SDKでの効果と遅延を測る。
2. DanとChatGPTの両方を、同じWi-Fi試験用ルーター等の制限へ通す。DanだけのSDP差し替えでは公式アプリとの公平な比較はできない。
3. 実家で問題が出た回線の統計を採る。合成した10%欠落がその回線を代表するとは仮定しない。

専用機の購入はこの準備・コード検証の前提ではない。
