## 比較結果

|質問|ChatGPT|Dan|
|---|---|---|
|尼崎で店内が24時間営業のマクドナルドを、公式サイトで一つ探す|2号線尼崎店を回答。公式ソースを表示し、催促なしで報告。画面にはWorked for 12s|web_search経由。約294msの結果処理後、33文字の未確認結果をLiveへ送信。「公式サイトで確認できる情報が見つからなかった」と自発的に回答|
|JR尼崎駅から、その店までタクシーなら何分か。目安でよい|「その店」を引き継ぎ、7〜10分程度と回答。地図を表示。画面にはWorked for 15s|再度確認し、「今のところ確認が取れなかった」と回答。新規の作業担当ジョブは作成されていない|

ChatGPTのWorked for表示はアプリ自身の値であり、発話終了から音が出るまでの実測値とは異なる。録音の自動文字起こしは誤認識・無音区間の幻覚があるため、単独では音声の反復や正確な発話開始時刻の証拠にしない。ChatGPTの最初の入力文字起こしも「近所の5時間営業」と誤認識していたが、回答は24時間営業として補正していた。Danは「二四時間」と文字起こしした。同じWAVでもモデルに渡った認識文は同一ではない。各一回の比較であり一般性能を断定しない。

ChatGPTの内部モデル構成・本当の検索開始時刻は観測していない。「発話中から検索を始めている」ことは、この試験からは確定できない。

## 取り入れるべき点と次の検証

1. 会話の文脈から「その店」「目安」を扱い、確認済みの事実と推定を分けて答える。検索結果を一律の厳しい判定で空にする現行経路を、実際の検索ペイロードから検証する。
2. 完了結果の取得と発話の各時刻を永続ログに残す。現在の端末logcatだけでは過去の不具合の区間特定ができない。前景・背景・無言待機の各条件で再現を調べる。
3. 一つの検索を別担当へさらに委譲して失敗する余分な経路を減らす。API・モデルの応答速度だけでなく、依頼全体の時間を見る。
4. 検索やページ確認の状態を短い一行で画面に出す。説明文やボタンの長いラベルを戻す必要はない。

## 修正と本番経路の追試（同日05時台）

実際の検索結果を再投入すると、旧Jev判定は公式の店舗ページをconfidence 0.98で不採用、口コミを0.95で採用した。問題の検索はAstra CLIへ到達していなかった。この根拠の採否・一段落選択の処理を撤去した。資料をそのままLiveへ送る案も実音声で試したが、「今開いているか」を読み解けず閉店中の店の営業時間を返す失敗が出たため、この案で完了とはしなかった。
