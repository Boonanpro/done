# LIVE 1：司令室と制作物エディターの評価（2026-09-14）

## 結論

司令室のバックエンドは実装上 GPT-5.6 Terra、制作物エディターは GPT-6 Astra。今回の小規模比較では、司令室を Astra に替えると総合的に改善するとは確認できなかった。Astra は受付と完了の区別を明示する傾向があり、Terra は応答が速かった。両方の実行用プロンプト・モデル設定は変更していない。

優先したいのは司令室の LIVE 1 向け指示の補強。バックエンドだけを変更しても、音声側の委譲判断・相槌・割り込み対応の指示は変わらない。エディターは既にこの役割分担が比較的明確で、Astra を維持するのが妥当。

## 実装確認

| 対象 | 音声 | 判断・ツール呼び出し | 評価 |
|---|---|---|---|
| 司令室 | `voice_live.py` の LIVE 1 用短文 | `voice_live.BACKEND_MODEL = gpt-5.6-terra`、Responses API | 部屋横断の照会・依頼を担当。音声の指示は一般的な会話向けで、司令室固有の役割・割り込み・結果の扱いが薄い |
| 制作物エディター | `editor_live.py` の LIVE 1 用指示 | `editor_reasoning.MODEL = gpt-6-astra`、Codex CLI | 相槌、割り込み、委譲、結果確認の区別が明確。編集対象や選択範囲の制約もバックエンドにある |

司令室の詳細指示は `voicelog_routes.py` がバックエンド用に組み立てる。音声セッションには `voice_live.INSTRUCTIONS` が渡る。実作業の `command_center.delegate` は対象の部屋へ依頼を送る処理で、受付は作業完了ではない。委譲先のモデルが Astra になる保証もない。

エディターは新しい発言で古い判断処理を無効化する仕組みを持つ。これは制作ジョブを止める操作とは別であり、プロンプトだけでなくアプリ側の制御も評価する必要がある。

## 実測方法と結果

実際のプロンプトとツール定義を使い、実 API でモデルを呼んだ。ツールの結果は架空データで返し、実際の部屋への依頼、編集、公開、制作中止は実行していない。司令室は進捗確認、過去会話の検索、タイトル変更依頼、直前の訂正、沈黙要求、対象の曖昧な発言を各条件 2 回評価した。エディターは制作中止、発話だけの停止、参照だけの指示、選択字幕だけの修正を各 2 回評価した。

初回の検索 fixture が検索語に関係なく結果を返していたため、その検索結果を品質評価から除外し、実装の部分一致方式に合わせた追加比較を行った。

下表は初回検索を除く司令室 5 ケース × 2 回の中央値。ツール結果は即時の模擬応答であり、時間はバックエンド API の所要時間の合計。実際の音声返答までの時間ではない。

| 司令室の候補 | 件数 | 最初の API 応答 | 最終応答まで |
|---|---:|---:|---:|
| GPT-5.6 Terra、推論設定未指定（現状） | 10 | 2.42 秒 | 4.46 秒 |
| GPT-6 Astra、推論設定未指定 | 10 | 3.63 秒 | 6.30 秒 |
| GPT-6 Astra、reasoning effort = low | 10 | 3.14 秒 | 6.00 秒 |

このサンプルでは Astra は約 1.5〜1.8 秒遅い。low 条件は別の時間帯・直列実行であり、キャッシュや負荷も統制していない。性能差を統計的に確定する数値ではない。

手動で意味を確認した結果：

- 進捗確認、タイトル変更、訂正では両モデルとも必要な制約を保持した。公開禁止を無視した呼び出しはなかった。
- Astra は依頼の受付後に「完了報告はまだ」と明示する例があった。Terra も「依頼しました」と返しており、作業完了を誤報したわけではない。
- 沈黙要求では Terra に不要な状態照会が 1 回あった。Astra の通常設定は 2 回とも空の回答だった。ただし空回答が実際の音声セッションで適切な沈黙になるかは未検証。low 設定は短い了承を返した。
- 対象が曖昧な発言では、両モデルとも変更操作をせず確認した。読み取り専用の一覧取得を挟む例はあった。
- 検索方式を修正した追加 6 回は全条件で対象を発見。Terra は長い検索句も使ったが、一致する句が含まれていた。今回の結果から Astra の検索成功率が上だとは言えない。
- エディターの 8 回は、制作中止と会話継続、発話だけの停止、参照と編集対象の区別、字幕の文字だけの変更について、意図に合うツール選択・引数だった。実際の制作物の変更結果を検証したものではない。

自動採点には、日本語の言い換えや許容できる読み取り操作を誤って失敗と判定する箇所があった。機械的な pass 比率をモデルの成功率として使用していない。生データはそのまま保存した。

## プロンプトの改善候補（未適用）

司令室：

1. 音声側にも「複数の部屋を横断して状況を把握し、担当へ依頼する役割」を短く示す。
2. 相槌、割り込み、発話だけの停止、通話終了、作業中止を区別する。ユーザーの訂正を最新条件として渡す。
3. バックエンドの受付結果と完了結果を区別し、結果前に成功を断言しない。
4. バックエンド側に履歴検索の部分一致方式を示し、検索句を適切に組み立てられるようにする。

エディター：

1. 現在の役割分担を維持する。
2. 制作担当に継承される共通指示と、音声担当が相槌を行う指示に重複がないか整理する。
3. 実音声で「やっぱりこちら」「見るだけ」「話すのを止めて」「制作を止めて」を確認する。今回の API 比較だけでは聞き取りや割り込みの体験を評価できない。

公式ガイドは LIVE 1 の話し方とバックエンドへの委譲を設計するための資料であり、アプリ全体のプロンプトを丸ごと置換するテンプレートではない。短い音声側の方針と、詳細なバックエンド指示、アプリ側の状態・履歴・キャンセル制御を分けて適用する。
