# 音声の最初の依頼と相づち

本人の10/31の「作業中も普通に会話したい」という依頼の続き。外部発信・スピーカー出力なし、専用試験部屋と専用メモだけを使う。

## 観測した不具合

- `.tmp/voice-response-length-trial/after.json`: 試験historyから安全条件の読み上げを外すと、質問への回答は約8秒。backend本文と音声の同時記録を開始。二重通知が唯一の原因とは言えない。
- `.tmp/voice-response-length-after/after.json`: 短い返答の方針を追加した試作。質問の文字認識が変わったため、速度の前後比較には使わない。
- `.tmp/voice-response-backchannel-after/after.json`: 「案内文を半分に」→「うん」→「何をお願いしたか覚えてる？」。依頼を復唱するが、native delegationが一度も発生せず、実作業は未開始。これまでの補完はjob受付後だけだった。
- `.tmp/voice-first-request-after/after.json`: 最初の依頼も補完する試作でstart_workを選んだが、後続の「うん」を条件変更として扱い、開始を拒否した。復唱はできてもメモは変わらない。成功扱いにしない。

## 変更

短い確認への返答は原則1文、詳しい説明の依頼は長さを制限しない。結果報告に次の手や未確認条件を毎回付ける指示を改めた。

既存の先読みが作業依頼と認識した時点から、native delegationが無い場合にも単一受付で判断を要求する。先読みは実行・許可・完了の証拠にならず、最新の発話を通常のbackendへ渡すだけ。送信不明の再試行なし。

保留中の操作へ新しい発話が届いていた場合だけ、先読みの既存判断接続を使って文脈を照合する。純粋な相づちと高い確度で判定された時だけ、先の依頼を有効なまま扱う。承認・拒否・訂正・質問・曖昧な結果・通信失敗はその例外に含めない。照合中にさらに言葉が届いたら判定を捨てる。相づちを承認に変えたり、作業内容を追加したりしない。後から届くnative/fallbackの重複実行も同じ受付で防ぐ。

## 検証

単一受付、訂正後の古い操作拒否、意味判定が遅れた時の新発話保護、承認を相づち扱いしない条件、最初の依頼の重複抑止を含む関連試験を実行。実音声の最終確認は `.tmp/voice-backchannel-admission-after`。

全体の快適な会話や本人端末の発声遅延の改善を、この限定試験だけで保証しない。別室stop_runの音声選択も別の確認対象。
