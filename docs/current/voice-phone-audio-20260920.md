# スマホ音声処理の分離と実機通信試験（2026-09-20）

## 反映した変更

Android APK 1.0.26 / versionCode 24。スマホ単体の音声源はAEC/NSをautomaticにし、端末の処理を利用可能にした。Atomの音声源はsoftwareを明示する。全通話でハードウェア処理を無効化していた設定を撤去。

同じPeerConnectionとADMを維持する。Atomからイヤホンへ切り替えた通話ではsoftwareを維持するので、今回の変更はスマホ単体の通話を対象にする。途中でfactoryを再生成したり、別のLive接続を増やしたりしない。

ネイティブライブラリ144.7559.14の実装・実機で、音声源のechoCancellationMode/noiseSuppressionModeを確認した。RNの制約はmandatoryの入れ子ではなく平坦なキーを渡す必要がある。旧OTAとの組み合わせでAtomだけ設定を失わないよう、runtimeを1.0.26へ更新。

変更箇所:
- `mobile/native/voice/DanExternalAudio.java`
- `mobile/native/voice/DanWebRtcAccess.java`
- `mobile/native/voice/DanWebRtcAudio.kt`
- `mobile/voice.tsx`
- `mobile/app.json`

## 検証

実際のDone部屋、Galaxy S25、同じ合成発話をPCスピーカーからマイクに投入。短い物語→割り込み→曜日→終了。会話内容と声の長さはモデルが生成するので完全に同一の音響条件ではない。外部マイク録音・ネイティブログ・WebRTC統計・Android AudioFlingerを保存。ASRが「猫」を「れいこ」等に誤認した試行もあり、正確性の全面合格ではない。

- スマホ設定: `aec=PLATFORM ns=PLATFORM aecMode=AUTOMATIC nsMode=AUTOMATIC`を実機で確認。
- Atom用設定: 同じAPKの診断版で音声源にsoftwareを指定し、`aec=SOFTWARE ns=SOFTWARE`を確認。Atom本体のPCMを使った再試験ではない。
- 通常接続: 更新前後とも会話・割り込み・音声終了が成立。更新前後の受信欠落は双方0。受信補完量は改善を示していないので、AEC変更で受信音切れが直ったとはしない。
- TypeScriptチェック、Android releaseビルド、既存の音声統計テスト3件が成功。
- 最終の通常APKでWi-Fi→モバイル回線→Wi-Fiを実行。再接続操作なしで曜日質問に回答し、音声終了でサービスも閉じた。切替中の送信欠落122・受信欠落2は残り、「無音断なし」の合格とはしていない。Wi-Fi設定を復元した。

## 今回新しくできた通信試験

一時的な診断APKでSDPの接続先候補だけをPCのUDP中継へ置き換えた。接続情報の受け渡しはADB reverseでUSB経由、実音声はスマホWi-Fi→PC→OpenAI。音声の暗号化は維持し、UDPパケットを単位として遅延・帯域制限・欠落を追加。対象はこの試験通話だけ。既存VPN・ルーター・ファイアウォール設定は変更していない。

これにより、前回のヘッドレス試験から進み、**実際のAndroid APKで**障害を注入できた。ただしChatGPTアプリをこの中継に通したわけではない。実家の回線条件と同一とも断定しない。

|条件|観測した最大RTT|受信欠落（最終定期計測）|補完サンプル増分 / 対象サンプル増分|
|---|---:|---:|---:|
|中継のみ|122ms|0|2,861 / 1,447,680|
|片方向64kbps、20±10ms遅延、最大3秒キュー|2,735ms|43|157,768 / 1,443,840|
|同条件 + 受信24kbps指定の試作|3,090ms|70|204,600 / 1,443,840|
|10%欠落、片方向120±80ms遅延|320ms|177|122,577 / 1,445,760|

帯域制限時には返答が細切れになり、通常設定の試行では終了指示後7秒の観察時間内にサービスが閉じず、試験の上限でアプリを終了した。10%欠落試験では会話と音声終了が成立したが、送信欠落384、受信欠落177を観測したため音質合格ではない。

制限下でも対象のAndroid再生トラックのunderrunは0だった。今回の条件では、ローカル再生バッファ枯渇より前の受信・ネットワークで問題が発生している。全ての実環境の音切れについて同じ原因だとは言えない。

24kbps指定は改善しなかったため本番へ採用していない。モデルの発話内容も変動するので、「指定が無視された」とも断定しない。交渉された音声コーデックはOpusでFEC指定あり、REDは応答にない。指定方法は[RFC 7587](https://www.rfc-editor.org/rfc/rfc7587.html#section-7.1)に基づく。

## 限界と次の切り分け

スマホ用の入力処理は改善候補を反映した。**外出先の受信音切れの解消は未達成**。ネットワーク制約で悪化することは実機で再現できたが、ChatGPTとの差が通信経路・混雑時の送信制御・復元処理のどれにあるかは未確定。

次は受信の実通信量・到着間隔を測り、帯域制限時にLive送信側が追従する条件を確かめる必要がある。ChatGPTも同じ制約で比較するには、今回のSDP差し替え方式ではなく両アプリを通せる共通の試験経路が必要。既存の保護VPNを不用意に解除する方法は取っていない。

証拠は `.tmp/voice-audio-separation/` の各試行JSON/WAV/native.log/flinger.txt、health.json、metrics.json、relay.json。試験限定のライブラリ変更を照合して復元し、診断ファイルとADB reverseを削除。最終APKにUDP中継・帯域制限・24kbps指定は含めない。テスト履歴は内容を確認したIDだけ削除し、deleted-tests.jsonlに控えを保存。

実施した8通話のテストメッセージ65件を削除。インストール済みAPKと通常版APKのSHA256一致を確認。Core再起動なし、API通話・UDP中継は終了、アプリを通常画面へ戻した。変更は実機にインストール済みだが、コミット・プッシュはしていない。
