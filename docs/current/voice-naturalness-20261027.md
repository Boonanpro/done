# LIVE1の相づちと読み上げ感（2026-10-27）

本人の依頼は相づち抑制の撤去と主因調査。変更は voice_live.INSTRUCTIONS の Backchannel policy だけ。発話途中の短い自然な相づちを認め、話す番を奪わない。声・モデル・他の規則は変更していない。新規セッションの組立で抑制文の不在と新文の存在を確認。開始済みセッションの instructions は更新せず、次の通話から適用。

## 実通話の証拠

2026-10-26 23:43〜23:47 JST、部屋 5e43d6b8-0f68-4113-a576-01bb39b84933 の会話と .tmp/voice-sideband.jsonl、.tmp/perf_events.jsonl を読んだ。本人は冒頭から「おつかれ」を繰り返し、「聞いとん」「反応遅くない」と呼びかけている。「あのー、LINE」「LINEのさ」「公式LINEのさ」の後にも「おい、聞いとん」と催促し、それからダンが応答。冒頭から23:44:36までバックエンド委譲なし。従ってこの区間の無反応を、別AIの回答生成待ちでは説明できない。

同通話の通信統計17サンプルのうちRTTのあるサンプルで往復0.109〜0.116秒、中央値0.110秒。受信音声バッファの累積平均は0.090〜0.171秒。数秒以上の無反応を通常の通信時間だけでは説明しにくい。ただし端末のマイク処理やBluetoothの遅れを除外する測定ではない。

会話履歴の時刻は保存時刻で、発話終了時刻ではない。speech_startは音声パケットの1.5秒の途切れを使っており、無音パケットが続く出力の発話開始検出として不十分。これらから正確な応答遅延を算出しない。音声本体は sideband が保存していないので、当該通話の抑揚を聞いたとは主張できない。

## 結論と未確定部分

無反応の有力原因は、話し途中の相づちを明示的に禁止していた会話方針。公式も全ての重なりを禁止すると相づちを抑制すると説明している。雑談はLIVE1が音声で直接返し、アプリに固定の返答待ちタイマーは見つからない。mobile/voice.tsxの2500msは文字起こしの保存待ちで、音声再生はWebRTCトラックが直接担当する。

読み上げ感は別途未確定。固定の声 meridian は公式で英語・北米・男性に分類され、日本語の男性声 shida が存在する。言語の適合は比較すべき要因だが、英語の分類だけで日本語の抑揚が悪いとは断定できない。「あ、そっか」等の禁止と過去チャットの文体も候補。声を変えた同条件の音声比較なしに主因確定・改善済みとは言わない。

以前の10月2日 c213e0c0 と35951e00では、そのまま読み上げる指示を撤去し、作業報告を材料として渡す形に変更済み。今回の雑談の症状にはそれだけでは不十分。
