# JevをDanのどこに使えるか：実APIによる検証

2026-09-17。入口・履歴・Web検索・ブラウザ・画面操作を検証した。
本番の音声受付は変更していない。予約取消・購入・外部送信は実行していない。

## 結論

Jevの適用をブラウザの末端に限定する理由はない。新規依頼の振り分け、
検索結果からの根拠選択、連続した画面操作で実動作を確認した。
ただし任意の依頼を無条件に実行させられる精度は確認できていない。
分類の採用と実行権限、画面内の値の計算とクリック選択を分ける必要がある。

これらは実Jevを使う有限サンプルの試験で、運用全体の成功率・p95保証ではない。
ブラウザ/画面試験では選択結果を隔離環境で実行し、最終DOMを別に読んで正誤を判定した。
厳しい自動採用基準を通過した試験だけを動かした結果ではない。確定ボタンは常に実行対象外。
したがって「6/6だから任意の本番サイトでも実行してよい」という結論には使わない。

### 今回の取消依頼そのもの

「新幹線の予約したやん、一昨日、十八日用の。あれキャンセルしてほしい」を
新規仕事判定に3回渡した。jev-latestの応答モデルはjev-1.13.0。

- 3回ともworkを選択。
- 所要1,855.09 / 382.86 / 417.28ms（初回は資格情報取得・接続を含む）。
- confidence .49 / .55 / .49、選択確率 .75 / .77 / .74。
- 既定の厳しい採用基準では3回とも保留。

今回の約25秒の窓口処理を0.24秒に置き換え、仕事全体を同じ精度で完了できたという証拠ではない。
3回の正解を見て採用閾値を引き下げる変更はしていない。
振り分けに成功した12例の引き継ぎ内容はユーザー原文そのもの。
対象予約・日付・承認をJevが生成したものではなく、担当側での確認は残る。

## 見つかった限界

- 広い分類では、通話終了の引用・否定と、本当に切る依頼を混同した。
- 進行中の仕事があると「新しい検索」か「条件の追加」か曖昧になるケースがある。
  30例中の1誤りはこの境界で、モデルだけの誤りと断定しない。
- OCRは誤選択した画面の時刻・価格を正しく読めていた。
  Jevが19時8200円を選び、21時6800円を見落とした。文字認識だけの問題ではない。
- 画面操作はOCRが1ステップ約0.5～1.8秒で主な待ち。
  DOMやアクセシビリティ情報を使える場合はそちらが有利。
- 既知の公式ページには根拠候補が重複しており、正解でもconfidenceが.48～.53だった。
  候補を排他的にする設計と、コードによる検証が必要。確信度だけでは品質を断言できない。
- 検索APIが適切な結果を返さない場合、Jevの選択だけでは回復しない。
  クエリ修正・別の検索・Astraへの引き継ぎが必要。

Choice / Score / Noulの型付き判断をコードで組み合わせる方式。
今回の試験はChoiceを使用した。自由文生成・任意引数生成の能力を検証した試験ではない。

## Danへの適用判断

1. 新規の実作業が明確な場合は、入口Jev＋コードで原文と会話を担当へ渡す候補になる。
   窓口Astraが詳細を調べて長い指示文を作ることを必須にしない。
2. 状態取得・履歴検索・単純なWeb検索は、取得をコードで行い候補選択をJevへ。
   回答はLiveへ根拠ごと渡す。生成内容の正確性は別途実会話で検証する。
3. 作業担当が必要な計画・判断はAstraへ一度渡す。独立した選択は1回の複数質問か並列呼出。
4. ブラウザはDOM/アクセシビリティ＋Jevを優先し、画面OCRは必要な場面で使う。
   値の計算・条件照合・終了判定・権限検査は可能な限りコードで検証する。
5. 新規作業受付、既存作業への更新、通話終了を混同しない検証を通してから本番接続する。

このターンで行ったのは実測と再現可能な評価コードの保存。
音声本番への入口Jevの組み込み、共通テキスト経路への適用、最終音声応答時間の改善は未配備。
購入/取消/送信やユーザーのブラウザ・音声デバイスは操作していない。
