# Dan高速化の合格条件（2026-09-17）

ユーザーの目的は、GPT-6 Astraの判断品質を維持しつつ、ブラウザと日常作業の不要な待ちをなくすこと。参考: https://github.com/awlevin/typesafe-computer-use 。MacのOCR/座標クリックを移植するのでなく、DanのDOM参照・条件検証・認証セッション・中断境界を使う。

## 目指す体験と受け入れ条件

1. **確認済みフォームを一息で埋める。** 8個の独立した通常入力を1ツールで実行。意味による欄選択が必要ならJevの1リクエストにまとめる。温まった隔離Chromium・ローカル画面・実Jevでp50 1秒以内、p95 1.5秒以内を目標。全値を機械照合、送信0回、欄の重複・変化・資格情報欄は実行前に拒否。
2. **既知の手順はクリックごとに考え直さない。** Astraが操作候補と結果条件を指定した6段階の手順を1ツールで実行。結果条件を毎段階検証。準備済みローカル画面でp50 6秒以内、p95 9秒以内。同じ操作・同じ最終結果の通常経路より2倍以上を狙う。モデル往復を除く比較はモデル込みと別記する。
3. **不確実なら即座にAstraへ戻る。** Jevに渡すのは既存の候補IDと必要な意味情報のみ。自由文生成、操作許可、購入・送信・削除の判断を移管しない。曖昧・候補外・API障害・画面変化・中断で残りを実行しない。実行済み操作は再送しない。API判断待ちの予算は最大1.2秒、全体停止までの余分な待ちを計測する。
4. **速さのために検品を削らない。** 対象・値・事後条件はコードで検証。必要な画像は残し、手順終了時に画面をAstraへ返す。API応答やJevのdoneだけでは成功扱いしない。重大な誤操作0件、既存のブラウザ回帰テスト合格、別文言の評価集合で採用判断の誤り0件を受け入れ条件とする。有限テストの0件は普遍的な品質保証ではない。
5. **待機や初期化の費用も減らす。** 通信接続を手順内で再利用。通常の既知のDOM操作では画像転送を明示的に省けるが、画像依存操作は画像を維持。静的な指示の読み直し、通知ポーリング、外部取得、メディア生成は別の計測単位とし、既に並列化・キャッシュ済みの改善を新規効果に数えない。

上記の秒数は初期合格目標であり、測定結果ではない。ネットワーク、サイト応答、ログイン、CAPTCHA、ユーザー応答、大型モデルの計画時間を除く条件は明記する。通常チャット全体が常に1秒以内になるという目標ではない。

実装後の測定結果と未達項目は[実測レポート](jev-speed-assessment-20260917.md)を参照。Jev判断の品質評価は、採用誤り0に加えて明確な例の採用率80%以上を要求する。全件棄却して品質合格とはしない。

## 技術上の境界

JevはChoice/Score/Noulを返す。複数の独立質問を同時処理できるが、後の画面を必要とする段階は直列。Choiceは最大255候補、入力は約32k tokens。自由文・コード・画像理解をAstraから移さない。confidenceは確率分布の集中度で、.9は正答率90%の意味ではない。

参考実装のREADMEは1判断0.13〜0.38秒、OCR込み1手約1.5秒と報告している。Danとの同一ベンチではない。参考実装は候補選択、少数質問の一括化、停止上限を活用している。一方、型適合・次画面への遷移だけではユーザーの目的達成を証明できない。Danでは実際の要素同一性、実行前後条件、途中失敗の履歴を保持する。

## 検証・配備

新しい評価は合成ページ/合成依頼で行い、ユーザーの実アカウント操作や購入を起こさない。実API料金が必要な試験は上限を具体化してから既存の許可範囲を確認する。編集側が参照する`typesafe_jev`と既存評価側の`typesafe`は別名であり、資格情報を勝手に複製しない。

コード保存・隔離試験・MCP公開・本番ロードの状態を区別する。Core再起動が必要なら実行中セッションとPID所有者を確認し、会話を切断しない。無関係な変更をコミットしない。
