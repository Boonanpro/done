# 2026-09-18 音声での取消処理の停止

## 実際の障害

ユーザーの予約取消依頼は23:52:31 JSTに作業として受理された。23:53:38、予約一覧の「払戻」を押して確認画面へ進む段階で、最終確定と誤判定して確認待ちになった。本人の承認発話は23:53:57に保存されていたが、作業状態に反映されなかった。23:58:48に作業が失敗した。予約取消は実行されていない。

確認待ちのMCP呼び出しを人の返事が来るまで保持していたため、実行側には道具が応答しない状態として見えていた。進捗にも「道具の応答が止まっている」と記録されていた。これをネットワークだけの問題として扱うのは誤り。

さらに、インストール済みAPKの表示版は1.0.25、Expo runtimeは1.0.10だった。1.0.25向けOTAは受け取れなかった。端末からAPKを取得してaapt2で確認した。旧クライアントが送らない発言完了フラグをサーバーが必須にしたことも承認を失う原因だった。

## 修正

- 確認待ちは永続状態に保存し、MCP呼び出しを即座に返す。待機中も読み取りは可能。
- Astraのターン終了と仕事の終了を区別する。承認・補足後は同じスレッドで次のターンを開始する。
- Smart EXの観測済み予約一覧遷移はorigin・path・実際のonclick・一覧表示で限定して識別する。最終確定は引き続き保護する。
- 進捗質問を条件変更と扱わない。曖昧な分類を勝手にupdateへ変換しない。
- 旧クライアントの承認は、提示後に保存された発言全文との一致を待って照合する。部分発話だけでは承認しない。
- 承認の意味判定が曖昧な場合は、対象の提案と返事に絞ったJev判定で確認する。確定権限の閾値は引き下げない。
- Windows上の読み取りとatomic renameの競合は保存操作だけ再試行する。状態変更関数を再実行しない。
- 空のバックエンド応答でも「考え中」を解除し、保留音が残り続けないようにする。
- APKのruntime番号を整合させて端末へ上書きインストール。OTA update ID `01a0aff2-0013-709e-b5c1-e831616eb194`を端末が読み込んだことを確認。
- 今後のビルドでAPK版とExpo runtimeの不一致を検出するGradleチェックを追加。
- 通話中のWebRTC接続状態と送受信量を、本文・認証情報を含めず端末から記録する。
