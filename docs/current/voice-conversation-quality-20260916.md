# 音声会話の基盤改善と実音声試験（2026-09-16）

目的はモデル交換や画面共有ではなく、現在の Live 1 と Astra CLI で会話・記録確認・実作業を安定させること。

## 合格基準と測り方

- 単純な質問・雑談：入力音声終了から応答音声開始まで 3 秒以内。
- 履歴確認：15 秒以内に記録に基づく具体的な回答を開始。「確認するね」は合格に数えない。
- 作業への追加指示：同じジョブへ届き、成果物に反映される。二重実行しない。
- 作業結果：完了前の成功宣言、繰り返す待機説明、重複した完了報告がない。
- 保存された記録と、外部サービスを今確認した結果を混同しない。

`scripts/voice_conversation_trial.py` は自然な日本語の合成音声を実時間で WebRTC に流し、Live 1 の音声、文字起こし、実際の Astra CLI・ツール・作業ジョブを記録する。既存 Done 部屋には書き込まない。ファイル作業だけ専用の「音声・イヤホン動作テスト」部屋と `.tmp/voice-conversation-trial/<試験名>/` を使用する。

記録は `.tmp/voice-conversation-trial/<試験名>.json` と WAV。`scripts/summarize_voice_conversation_trial.py` で集計できる。PCM 開始時刻と、具体的な回答の文字起こし到着時刻は別々の指標。後者は発話開始の近似であり、厳密な音素境界ではない。物理マイク・イヤホン・携帯回線の試験ではない。

## 再現した原因と修正

1. 会話検索から Done 自身が除外され、project_id による絞り込みも無視されていた。所有権を保ったまま両方を修正。検索結果は該当部分を返し、元の全文は保持する。
2. 「まだ？」などの追加発言で未実行の読み取りまで無効化していた。読み取りは継続し、変更を伴う操作だけ新しい指示との整合を確認する。
3. 作業担当の全文完成まで音声への結果が待たされていた。最終回答の完成した文から SSE で届ける。思考や途中の着手説明は最終回答に混ぜない。訂正後の回答を落とす不具合も修正。
4. 独立した作業担当に読み取り専用の設定が渡り、ファイル作成を断る例を再現。作業担当だけ workspace-write に変更。エディター窓口と音声窓口の既定は変更しない。外部操作の確認境界は維持。
5. 作業依頼全文・途中経過・完了結果を同様に渡し、完了前に「保存した」と発言する例を再現。音声には依頼文の再掲ではなく状態と実際の報告を渡す。履歴用の完全な記録は別に保持。
6. 受付済みの仕事を窓口が何度も確認し、作業結果の自動配達と重複していた。道具の説明に自動配達の契約を明示し、不要なポーリングをなくす。
7. 通常のファイル作成でも任意コード実行を選び確認待ちになる例を再現。道具の説明で通常のファイル操作に適した道具を明示。任意コードの確認を無条件には解除しない。
8. 追加発言の文字起こしが届いても Live の委譲イベントが出ず、依頼が作業に反映されない例を再現。作業中に始まった発言は、確定した文字起こしを Astra に届ける補完経路を設けた。通常の委譲と発言単位で重複排除し、発言がさらに続いた場合は続きを届ける。携帯のバックグラウンド tick でも動作する。正規表現による変更意図の判定や追加 API モデルは使わない。
9. 状態更新を毎回 thinking に追加すると、Live が待機説明を繰り返すことを再現。途中状態はアプリに保存し、次にユーザーが話し始めた時に最新情報を渡す。完了・失敗・本人への確認は即時通知する。
10. 作業受付の最終文を「仕事の完了」として通知しない。作業の完了報告はジョブ結果の配達に一本化する。
11. 作業受付から開始まで約75秒待つ例を再現。Core への起動通知を、重複実行しないキューの取得処理に限って再試行する。同期のプロジェクト取得でイベントループを塞いでいた箇所もスレッドへ移した。実際の作業操作は自動再試行しない。
12. 完了直後に遅れた定期更新が到着し、DB の状態を「実行中」に戻す競合を確認。定期更新は DB 上でも非終端の状態だけを更新する。影響を確認した専用テスト部屋の3件のみ、実際の完了記録に合わせて修復した。

モデルは Live 1 / GPT-6 Astra のまま。窓口の Astra は high を維持し、CLI の fast tier を使用。API の別モデルによる判定は追加しない。
