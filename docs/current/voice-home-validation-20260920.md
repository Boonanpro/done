# 自宅での音声比較・遅延分解（2026-09-20）

## 結論と適用範囲

検索待ちの大きな要因は、Jev → 検索取得 → Astraによる資料読解という直列処理、および追い質問にも再検索すること。実家の音切れの単一原因は未特定。Atom由来のソフトウェアAEC/NS設定は入力欠けの有力な比較候補だが、通信障害の原因と断定しない。

本番ロジックの修正・完成報告ではない。スマホに一時的な診断APKを入れて比較後、元のAPKへ復元した。Coreの再起動なし。恒久的なネットワーク設定変更なし。

## 検索の実測

実際のLive音声入力、現行Doneの履歴・Jev受付・Astra読解・検索APIを使うヘッドレス試験。外部操作は検索・履歴読取に限定。スマホの無線・音声ハードウェアを測る試験ではない。

|工程|最初の質問|追い質問|
|---|---:|---:|
|Jev判断自体|0.715秒|0.657秒|
|受付全体|1.188秒|0.688秒|
|検索取得|3.515秒|5.531秒|
|検索後のAstra応答完了|5.891秒|4.234秒|
|質問の音声終了→最初の回答要点|10.766秒|10.562秒|
|最初の回答要点→出力音声開始|1.094秒|0.984秒|

「東京国立博物館の今週の土曜日の開館時間」「じゃあ日曜日も同じ時間まで？」を使用。後者の検索クエリーは直前の回答と質問の連結で、博物館名が抜けていた。Astraは自分の会話文脈で対象を維持して回答したが、対象のないクエリーで再検索する設計は余分な待ち・検索品質低下を招く。

試作では、2問目の検索結果を1問目に実取得した資料で置き換え、同じAstraへ渡した。質問終了→要点は3.812秒、資料読解完了は2.953秒。9月27日17時閉館・最終入館16時30分という回答は維持された。これは試験側で再利用可能なケースを選んだ1組の比較であり、汎用的なキャッシュ振り分けを実装済みという意味ではない。初問のAstra応答は別走で10秒に増えたため、モデル時間の揺れもある。差の全てを検索省略だけに帰属させない。

「今週土曜日」を両試験とも次の9月26日と解釈した。週の解釈について本人確認していないため、日付解釈を含む完全な正確性合格とはしない。

証拠: `.tmp/voice-conversation-trial/network-latency-{stages,reuse}.json` とWAV、`.tmp/voice-network-20260920/{latency-stages,reuse-stages}.log`。

## ChatGPTアプリとの実録音比較

同じGalaxy S25・自宅Wi-Fi・同じ合成発話で、公式の店内24時間営業店舗を1件検索。両方とも2号線尼崎店を回答した。外部マイクの録音をWhisperで区間推定すると、本回答の開始は録音開始からDan約19秒、ChatGPT約16秒。1試行ずつ、ASRの粗い区間境界なので精密な3秒差・平均性能とはしない。ChatGPT内部のモデルや処理経路は見えていない。

Danのこの試行の送受信パケット欠落は0、RTT約111–112ms。音声側の結果受領→発話イベントは603ms。末尾のメンテナンス日の表現はアプリ記録と外部ASRの両方で崩れており、別途改善対象。ASR自体にも地名の誤認があるため、ASR文字列を発話の逐語的な正解とは扱わない。

証拠: `.tmp/phone-app-comparison/network-wifi-{dan,chatgpt}.{wav,asr.json,json}`。ChatGPT試験チャットは削除済み。

## スマホの音声処理比較

同じAPK内で起動時の診断ファイルによりADMを切り替えた。生成済みAndroidソースだけを一時変更し、canonical nativeソースは変更していない。

|構成|回数|割り込み「ちょっと待って」部分の保存された認識|
|---|---:|---|
|現状: ソフトウェアAEC/NS、Atom用callback/sinkあり|3|「短く…」「待って…」「待って…」と冒頭が欠けた|
|ハードウェアAEC/NS、同じcallback/sinkあり|3|3回とも「ちょっと待って…」から記録|
|標準ADM、Atom用callback/sinkなし|2|2回とも「ちょっと待って…」から記録|

GalaxyでハードウェアAEC/NS双方の対応をネイティブログで確認。speaker出力選択もスクリーンショットとAudioManager dumpで確認。試験は通常の短い雑談→応答開始を観測→約0.8秒後に同じ合成発話で割り込む。モデルの発話内容・長さは固定していない。試験中に履歴が蓄積したため会話文脈も完全同一ではない。初回群の外部マイクASRは主に投入音声のみを認識し、出力音質を定量評価できなかった。従って上表は認識の差であり、音質や全体の反応速度の改善を保証しない。

この結果は「ハードウェア処理をスマホで使う」候補を支持する。AtomはAndroidのハードウェア処理後にPCMを注入するため、全経路を単純にハードウェア処理へ変更するとAtom側のエコー処理を失う可能性がある。経路ごとの設計・検証が必要。

証拠: `.tmp/voice-network-20260920/dsp/` の profileログ、JSON、native.log、WAV、hardware-2-screen.png。

## 通信障害の再現

Windowsの共有Wi-FiはcapabilityがEnabledでも実起動がWiFiDeviceOffで2回失敗した。物理Wi-Fiプロファイルを明示しても同じ。WinDivertを使うスマホ限定・時間制限付きのプログラムは準備したが、管理者権限もなく未実行。ネットワーク全体の設定や保護用VPNを解除していない。

CDPのWebRTC packetLoss指定も試したが、100%指定で通常の音声が通った。今回の環境では障害注入として有効と検証できず、不採用。

代わりに、OpenAIから返るICE候補を専用のローカルUDP中継に置き換えたヘッドレス実音声試験を実施。DTLS/SRTPはそのまま中継し、データ内容は改変せずパケット単位で欠落・遅延を追加。中継の実カウンターとWebRTC両端の統計で注入を確認した。

|条件|観測|
|---|---|
|中継のみ|主要経路1783パケット転送、欠落0。受信・送信とも欠落0、RTT約118ms|
|10%欠落、片道120ms±80ms|主要経路123パケット破棄。受信48・送信82欠落、RTT約370ms。補完サンプル増加|
|8秒遮断→復帰|全中継合計578パケット破棄。送信欠落413。新しい接続を作らず次の曜日質問に回答|
|片方向ごと32kbps、最大3秒の待ち行列|受信欠落236、RTT約3.12秒。音声補完約40万サンプル。低帯域で遅延・途切れが大きくなることを再現|

これは実パケットを制御した試験だが、スマホAPKとChatGPTアプリを同じ制限下で比較した試験ではない。実家の特定の無線・VPN・基地局・経路条件も完全には再現していない。

証拠: `.tmp/voice-network-20260920/net-relay-*-relay.json`、`.tmp/voice-conversation-trial/net-relay-*.{json,wav}`、udp-shaper.py、relay-trial.py。
