# 粗い3Dと完成見た目を分ける実証

## 結果

既存Three.jsデモの人物・試作車・作業台を使用。人物が3秒で近づき、1.5秒でしゃがみ、1.5秒待つ6秒の配置データを保存。静止したカメラ。

組み込みimagegenで最初の3Dフレームを参考に、実写映画風の人物・金属車体・作業場・照明の画像を作成。元のフレームより人物等が大きく、画角は厳密には保持されていない。画像をユーザーが品質承認したわけではない。

Google直結gemini-omni-1.1-flashで各1本、720p、希望6秒を生成。

|条件|生成リクエストから保存まで|実際の尺|
|---|---:|---:|
|A：3D動作映像＋完成見た目画像|56.0秒|6.037333秒|
|B：同じ画像＋同じ動作の文章|32.5秒|6.016秒|

両方とも実写風の見た目、歩く→しゃがむの流れが成立。Aは短い移動、Bは車輪の近くまで移動し、終点が異なる。Bでも今回の単純な指示は成立した。各1例であり3Dの普遍的優位・厳密な時刻/座標一致は証明していない。高品質やユーザーの好みの合格判定でもない。

比較の判断は0/2/4/5.8秒の実フレーム、ブラウザで全尺再生成功、共通シーク、ネイティブ合成器のフレーム出力確認による。音声内容の聴覚検品は未実施。料金は領収データにusageを保存、請求額未確認。Higgsfieldは不使用。生成映像の人物・背景は画素であり内部3Dを直接編集できるわけではない。

## 実装

- scripts/export_conte_scene.cjs: 保存した配置データから独立ブラウザコンテキストで時刻を固定し、映像用フレームを出す。ユーザーのlocalStorage/会話に触らない。FFmpegはそのフレームを動画ファイルに符号化するためだけに使用。
- google_video.generate: edit対象動画とappearance_reference_pathを別々に渡せる。両ファイルの内容がキャッシュキーへ入り、見た目変更時に古い結果を返さない。二重課金防止の既存receiptを維持。
- timeline MCP generate_video: 同じ引数を追加。Higgsfieldで未対応の引数を黙って無視しない。
- scripts/run_conte_finish_proof.py: 上記A/Bの実行。既存結果を再使用、結果不明の課金リクエストは自動再実行しない。
- scripts/register_conte_finish_proof.py: 独立比較タイムラインへ3D映像/静止画/A/Bを配置。元の3D JSONへの対応も保存。既存ユーザー作品を変更しない。

Google仕様参照: https://ai.google.dev/gemini-api/docs/omni （source videoとreference imageの明示）

## 制作方法としての採用条件

まず画像で人物・背景・光・質感を確認する方法は有効。3Dは移動や位置関係を見て決めたい時、同じ空間で複数ショットを作る時の候補。単純な1ショットは画像＋文章でも成立し、今回はこちらが速かった。

参考選びをJevで行った試験ではない。GenHQの手法を既存デモへ接続する試験であり、上流の会話・検索品質や全ジャンルの仕上がりを証明しない。この結果を万能ルールにせず制作レシピの適用条件として保持する。

次の設計は、シート→内容/演出設計→必要に応じ完成画像/3D→通しVコンテを同じ作品の状態として持つこと。全作品に3Dを強制しない。完成動画の生成は待ち時間を伴い、生成済み実写映像の任意変更がリアルタイムになったわけではない。
