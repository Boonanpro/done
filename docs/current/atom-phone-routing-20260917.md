# Atom・イヤホン切り替えと作業待ち音（2026-09-17）

> この文書は初期のPC中継方式の検証記録です。同日後半にスマホがLive接続を持つ方式へ移行しています。現在の実装・配備・未達項目は [phone-owned-voice-acceptance.md](phone-owned-voice-acceptance.md) を参照してください。以下の「採用していない」は当時の判断です。

## 体験と構成

会話の接続はPC側Live 1に一つだけ維持する。スマホはAtomのTCP音声を認証付きWSSで中継し、Bluetooth通話イヤホン接続中の会話では入力・出力をスマホのAudioRecord/AudioTrackへ切り替える。Atom使用中にスマホの録音・再生・音声フォーカスを占有しない。

「スマホ自体がLive接続を持つ」という先の案は採用していない。既存のLive接続を維持することで、経路変更を会話の再生成や作業の再委譲にしない。スマホ単独の既存Live通話は別モードとして維持し、デバイス中継中の同時起動を防ぐ。

この段階ではAtomとスマホを同じWi-Fiで使用する。PCはインターネット経由のWSSを受け、従来のAEC・呼びかけ検出・音声会話を継続する。外出先ではAtomへのテザリング設定とIPの取得が別途必要。外出先のAtomまで検証済みとはしない。

## 実装

- `DanAtomRelay.kt`: 48kHz/mono/16bit、既存DAN4/OKF4の972バイトフレーム。Bluetooth SCO/LE Audioを利用可能な通信機器から選び、通話・フォーカス喪失中はDanのPCMを無音にする。古い接続のコールバックが次の接続を止めないよう世代を照合する。
- `atom_relay_routes.py`: JWTとデバイスの部屋への所有権を検証。ペアリング情報はTLS経由で所有者だけに返す。音声WebSocketはlocalhostの中継へ渡す。モデルのAPIキーは端末へ渡さない。
- `wifi_bridge.py`: スマホ中継は排他的な接続。入力キューと送信キューを制限し、切断・不正サイズを処理する。PC直結から中継への移行時はデバイスのboot/revisionを保持する。
- `work-waiting.ts`: 実作業が1.2秒以上続いていて発話がないときだけ小さな波音。単なる沈黙、確認待ち、完了、失敗、切断では鳴らさない。発話と実音声のレベルで停止する。
- Webの波音はAtomへの出力と同じ経路に混ぜるため、既存AECにも再生参照が渡る。スマホ単独通話ではネイティブMediaPlayerを使用する。

状態設計は `rule/canonical-verb` と `rule/cover-reachable-states` に従い、接続開始・接続中・使用中・停止・切断エラーを表示する。サービス通知から停止できる。部屋や作業は経路切り替えで変更しない。

## 9:30 の実機確認

USB再認証後、GalaxyとBluetoothイヤホンDG036-01を確認。最初の中継試験はheadset経路への移行後、13フレームでIllegalStateExceptionとなった。送信キュー約120ms超過を接続終了としていたことが直接原因。混雑中もAtom入力を読み続け、キュー上限を超えるフレームを捨てて会話接続を維持するよう変更した。失敗種別・フレーム数の診断を追加し、音声内容・秘密情報は記録しない。

修正版のAndroidリリースビルド成功、Galaxyへ上書きインストール成功。中継接続は待機状態で継続し、foreground serviceも確認。発話・イヤホン音質・同一セッション中の往復切り替えはユーザーの実機発話を待って確認する段階。最初の失敗試験ではブラウザ音声接続も再作成されたため、これを「同一通話を維持できた」と扱わない。

## 10:35 イヤホン単独の会話不成立

YouTube再生前に「もしもし」の後で返事がないというユーザー報告。Androidは10:35:19から58までVOICE_COMMUNICATIONの録音継続・not silencedを記録。PCブリッジにも有意なマイクRMSが届いたため、マイクが完全無音という仮説は否定。ただし音声入力に最大2812msの到着空白とその後の集中到着がある。Live側ログは挨拶のみでuser_speechなし。

イヤホンのAudioRecord.READ_NON_BLOCKINGをAtom受信ループから呼んでいた設計を修正。専用録音スレッドでREAD_BLOCKINGにより10ms音声を組み立て、直接WSSへ送信する。Atomは状態ヘッダー・物理接続確認を供給し、イヤホン使用時は二重送信しない。Atomの状態フレームが1秒以上途切れた場合は古い状態で送信を継続しない。世代と録音インスタンスを確認して古いスレッドが次の通話へ混ざることを防ぐ。録音解放前に共有参照を切り、通常終了を録音障害と誤判定しない。

録音フレーム数・RMS・実際の入力デバイス種別・送信ドロップ数を2秒ごとに記録する（音声内容は記録しない）。Androidリリースビルド成功、Galaxyへインストール、中継待機を確認。実際に返事が戻るかはまだ未検証であり、到着空白の全原因やモデル側無反応の原因が特定済みとは扱わない。

## 10:47 の会話成立と、通話画面の統一

ユーザーがイヤホンで会話できたと確認。Android録音はBluetooth SCO入力で約200フレーム/2秒、送信ドロップ0。起動音なし、音の途切れ感、音声で終了できない点は残る。実チャットには「OK、電話切って」と「了解、切るね」があるが、対応する待機処理は発生していない。認識できていない問題ではなく、発話と終了処理がつながっていない。なお10:35の実チャットにもユーザー発言があり、上記の疎なLiveイベントログにuser_speechがないことを、音声認識されなかった証拠として扱わない。

中継通話画面を通常の音声画面と同じ球体・スタイルに統一。VoiceOrbとvoice-call-stylesを両経路で共有し、通話時間、ミュート、最小化、赤い終了ボタンを表示する。終了ボタンと通知の終了操作は、Atomの現在のboot/revisionに対するSTOPを送り、デバイスの待機への遷移を通じて既存Live接続を終了する。中継自体は残す。5秒で応答がなければ終了失敗を表示して再操作可能にする。

モバイル型検査、既存デバイス状態テスト4件、Androidリリースビルド成功。Galaxyへの上書きインストール成功。その直後にUSB接続がなくなったため、新画面の実表示と終了ボタンの実機確認は未完了。音声での終了、起動音、音の途切れはこのUI修正で解消したとは扱わない。

11:48 USB再接続後に中継を起動。実機で通常音声と同じ球体・経過時間・ミュート・赤い終了ボタンを確認（`.tmp/dan-relay-orb.png`）。アプリを再表示した際も通話画面へ戻る。終了ボタン試験中に端末が別画面へ切り替わっていたため、タップの到達は未確認。11:49:48.737にAtomの要求がfalse・revisionが2になり、11:49:49.237にブラウザ切断、49.312にLiveセッション終了。接続終了自体は確認したが、その原因を当該タップと断定しない。
