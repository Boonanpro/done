# 提案書デザインスキル

提案書・企画書を**プロのビジネスデザイナーが作ったような品質**のHTMLとして生成し、チャット画面にiframeで埋め込み表示するスキル。

---

## 出力ルール（厳守）

### ファイル保存とリンク

1. 生成したHTMLを `D:/dan-workspace/proposals/` に保存する（write_fileツール使用）
2. ファイル名は `{プロジェクト名}-proposal.html`（英数字ケバブケース）
3. チャットに以下の形式でリンクを表示する（別タブで開かれる）:

````
```proposal
ファイル名.html
```
````

### HTMLの技術制約

- **完全自己完結**: 外部CSS/JSファイルへのリンク禁止。Google Fontsのみ外部読み込み可
- **1ページ縦スクロール**: ページ切り替え・ページネーション禁止。全コンテンツを1ページに収める
- **横はみ出し禁止**: `overflow-x: hidden` を body に設定。全要素が画面幅内に収まること
- **レスポンシブ必須**: PC（960px+）/ タブレット（680px）/ スマホ（420px以下）の3段階
- **別タブ表示前提**: ブラウザの別タブで全画面表示される。iframe制約はない
- **フォントサイズ**: 本文14px、見出し最大28px。単独ページとして読みやすいサイズ

## デザイン原則

### 設計思考（コーディング前に必ず考える）

1. **誰に向けた提案か**: 相手の業界・立場・関心を理解し、トーンを合わせる
2. **一言で何を伝えるか**: 提案の核心を1文で定義。それがヒーローセクションになる
3. **相手に何をしてほしいか**: 承認・検討・フィードバック — CTAを明確にする

### タイポグラフィ

**絶対に使ってはいけないフォント**: Arial, Inter, Roboto, system-ui, sans-serif単体指定

**使うべきフォント（Google Fontsから選択）**:

| 用途 | 推奨フォント |
|------|-------------|
| 日本語見出し | Noto Sans JP (weight 700-900), M PLUS 1p, Zen Kaku Gothic New |
| 日本語本文 | Noto Sans JP (weight 400), BIZ UDPGothic |
| 英数字アクセント | JetBrains Mono, IBM Plex Mono, Space Grotesk, DM Sans |
| KPI数値 | JetBrains Mono, Oswald, Barlow Condensed |

フォントは**最大2種類**。見出しと本文で差をつける。数値にはモノスペースを使い、桁が揃って見えるようにする。

### 配色

- **支配色1色 + アクセント1色 + ニュートラル**: 3色で構成する。均等配分は禁止
- 支配色は面積の60%以上を占める。アクセントは要所にだけ使い目を引く
- ダーク/ライトどちらでも良いが、**中途半端なグレー背景は禁止**。コントラストを明確に
- CSS変数で色を管理する:

```css
:root {
  --bg: #0d0d0d;          /* 背景 */
  --surface: #161616;     /* カード等の面 */
  --border: #252525;      /* 境界線 */
  --text: #e8e8e8;        /* 本文 */
  --muted: #888;          /* 補足テキスト */
  --accent: #e8a020;      /* アクセント（提案ごとに変える） */
  --accent-subtle: rgba(232, 160, 32, 0.10); /* アクセント薄 */
}
```

**毎回同じ配色にしないこと。** 提案の内容・業界・トーンに合わせて配色を変える。金融=ゴールド、テック=ブルー、ヘルスケア=グリーン等、文脈に応じた色を選ぶ。

### レイアウト

- **情報密度を高く**: 余白は適度に。スカスカ禁止、ギチギチも禁止
- **グリッドを活用**: 2カラム・3カラム・4カラムを適材適所で使い分ける
- **セクション間に明確な区切り**: borderかpadding/backgroundの切り替えで区切る
- **カードの角丸は控えめ**: `border-radius: 4-6px` まで。大きな角丸は素人っぽくなる

### 背景と視覚効果

- ベタ塗りの単色背景は避ける。**微妙なグラデーション・テクスチャ**を加える
- ヒーローセクションには `radial-gradient` や `linear-gradient` でリッチさを出す
- `::before` / `::after` 疑似要素で光彩・グロウ効果を控えめに加える
- **アニメーションは不要**。iframe環境では再生タイミングが制御できないため静的に

## 提案書の構成（推奨セクション）

全セクションを必ず含める必要はない。提案内容に合わせて取捨選択する。

| # | セクション | 内容 | デザインパターン |
|---|-----------|------|-----------------|
| — | **ヒーロー** | タイトル・サブタイトル・KPI 3-4個 | 全幅背景 + グリッド |
| 01 | **結論** | この提案で何が実現するか（3行以内） | 本文テキスト、強調はinline style |
| 02 | **背景/課題** | なぜ今これをやるのか | カードグリッド or 箇条書き |
| 03 | **提案内容** | 具体的に何をするか | フローチャート or ステップリスト |
| 04 | **収益/効果** | 数値で示す期待効果 | テーブル + プログレスバー |
| 05 | **ロードマップ** | フェーズ分けの実行計画 | 横並びフェーズカラム |
| 06 | **体制/コスト** | 誰が何をやるか、いくらかかるか | 2-3カラム（体制・コスト・リスク） |
| 07 | **リスクと対策** | 想定リスクとその対策 | テーブル + バッジ（高/中/低） |
| — | **CTA** | 承認ボタン・次のアクション | 全幅背景 + ボタン |

### ヒーローのKPI表示

- 数値は**大きく太く**（18px+, font-weight 700）、ラベルは小さく薄く（9px, muted色）
- 3〜4個が最適。5個以上は詰め込みすぎ
- 金額・パーセント・日数など、提案の核心を一目で伝える数値を選ぶ

### CTAセクション

- 「承認する」ボタンには `window.parent.postMessage()` で親ウィンドウに通知
- ボタンはアクセント色ベタ塗り + ダーク文字。ホバーで明るく
- 「保留・修正依頼」のセカンダリボタンも並べる

## やってはいけないこと（アンチパターン）

- **角丸カードの羅列だけで構成する**: 情報の優先度が全て同じに見える
- **全セクションが同じ見た目**: セクションごとにレイアウトを変えてリズムを作る
- **絵文字をセクションアイコン代わりに多用する**: 素人感が出る。使うなら最小限
- **色を均等に散らす**: 支配色を決めてメリハリをつける
- **フォントサイズが2段階しかない**: 最低4段階（KPI数値 > 見出し > 本文 > 補足）を使い分ける
- **中途半端な余白**: セクション間の余白とカード内の余白に一貫性を持たせる
- **テキストの壁**: 長文は禁止。箇条書き・テーブル・カードに分解する

## レスポンシブ対応（必須）

```css
/* タブレット */
@media (max-width: 680px) {
  .two-col, .three-col, .four-col { grid-template-columns: 1fr 1fr; }
  .hero-inner { grid-template-columns: 1fr; }
}

/* スマホ */
@media (max-width: 420px) {
  .two-col, .three-col, .four-col { grid-template-columns: 1fr; }
  body { font-size: 11px; }
}
```

- グリッドは `grid-template-columns` で段階的に折り返す
- テーブルが横に溢れる場合は `overflow-x: auto` を親要素に設定
- ヒーローのKPIは横並び → 折り返しに変更

## 自己評価ループ（品質保証の仕組み）

このスキルには **生成→評価→改善の自動ループ** が内蔵されている。

### 関連ファイル

| ファイル | 役割 | 誰が更新するか |
|---------|------|---------------|
| `criteria.md` | 品質基準（M1-M5必須 + Q1-Q5品質スコア） | 人間（たまに） |
| `learned.md` | 蓄積された改善パターン | ダン（毎回自動） |
| `actions/create.md` | 自己評価ループ込みの作成手順 | ダン（Level 3到達時） |

### ループの流れ

```
learned.md参照 → 初版生成 → 視覚評価(screenshot) → 採点
→ 不合格なら改善(最大3回) → 合格したら出力 → learned.mdに記録
```

### 詳細手順

`check_skill` で `create` アクションを確認すること。手順の全ステップが記載されている。

### 品質チェックリスト（簡易版）

- [ ] 横スクロールが発生していないか
- [ ] スマホ幅（375px）で全セクションが読めるか
- [ ] フォントがArial/Inter/Robotoになっていないか
- [ ] KPI数値が一目で読み取れるか
- [ ] セクションごとにレイアウトが変化しているか
- [ ] 配色が提案内容に合っているか
- [ ] CTAボタンが明確に存在するか
- [ ] テキストの壁（5行以上の連続段落）がないか
