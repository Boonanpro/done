## 操作の選び方

- `inbox.py draft <id> --intent <要旨>` に標準入力で本文を渡すと、顧客チャットの下書きを更新できる。直前に読み直し、edited_by_ownerの本文を保持する。
- `note <id>` は内部の一言、`propose <id> --title ...` は本人への判断依頼、`did <id> --title ...` は実行済み結果。これらは対外送信ではない。顧客管理で頼まれたことへの返事はその顧客の場所に置く。
- 相手へ送る場合はcompose_messageの提案・送信の仕組みを使い、既存proposal_idと最新文面を引き継ぐ。顧客管理に下書きがある時は別カードを重複作成しない。契約・請求の状態更新が付随する送信は顧客管理の送信操作を使い、別経路で送ったなら送信記録を照合して重複を防ぐ。
- 画面のボタンはDanのbrowserでダンが押せる。操作前にMAPと実画面から対象顧客・段階を確かめる。音声でも、本人へボタン操作を差し戻さず同じ作業を進める。通話画面での操作の接続・成功は別途実際に確認し、スキルを作っただけで通話対応済みとは言わない。

APIを使う場合は、既存の認証済み経路と現在の `_server/routes.py`、`api.ts` で入力と副作用を確認する。URLや認証を推測して直接DBを書き換えない。以下は2026-10-31に確認した処理の違いであり、実行時にも確認する。

| 操作 | 副作用・注意 |
|---|---|
| offer-draft | カレンダーから候補を作り保存。既存候補の下書きを置き換えるので本人編集を保護する |
| confirm | カレンダーへ予定作成または移動、リマインド設定、確定文の生成。確定文を送ったこととは別 |
| unconfirm | カレンダーの既存予定を削除し、リマインドを取消。新規候補を作るだけのつもりで呼ばない |
| contract-draft | 未署名契約を無効化して月額ひな形で再作成。個別修正済み・単発ローンチ契約を壊さない |
| invoice-draft | 送信可能な請求書と文面の準備。送信とは別 |
| dan-draft/send | 最新下書きを送り、契約・請求URLが含まれる場合は対応する状態も進める |
| invoices/{id}/paid | 入金記録に加えてお礼の送信が起こり得る。承認なしの送信を起こさない |
| contracts/{id}/end | 契約・カード課金への影響を確認し、本人の指示範囲だけで行う |

送信や作成の応答が途切れた時は、現在の文面・送信結果・書類番号・カレンダー予定を読んでから再実行を判断する。成功した可能性がある操作をそのまま繰り返さない。
