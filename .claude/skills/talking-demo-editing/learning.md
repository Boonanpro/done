# 本人の指摘から、この手順書を育てる

本人は、動画を見て気づいた所を言葉で指摘する。指摘は、その版の直しの依頼であると同時に、その案件のテイストか本人の物差しを1つ教わったということ。指摘のたびに、(1) 部屋の担当が同じ決まりをその動画の全編に当てはめ、(2) 裏の学習の仕事が、まず案件の決まりとして残し、どの案件でも通じると分かった物だけをこの手順書の本文に上げる。本人が同じことを2回言わずに済み、まだ指摘していない所も直っていて、しかも別の案件・別のテイストの動画には持ち込まれない状態を作るのが目的。

本人は映画や別のテイストの動画も作る（2026-11-09 本人「中村さんの動画への指摘を全部の動画のやり方にしたくない。でも中村さんの動画のテイストはちゃんと定まっていってほしい」）。

## 部屋の担当がすること（動画を直して渡すたび）

1. SKILL.md の「指摘を受けた時」に従って直し、同じ決まりを全編に当てはめる。
2. 渡す前に、前の版の後に本人が書いた言葉を記録する。
   ```
   python /Users/mikihonda/done/scripts/video_learning.py pending
   python /Users/mikihonda/done/scripts/video_learning.py record --feedback <指摘のid …> --other <ほかの話のid …> \
       --applied "<指摘から作った決まりを、言われていない場面のどこに当てはめたか（納品版の分・秒）。無ければ理由>" --video "<版>"
   ```
   `--rest-other` は、指摘として挙げた以外の発言を全部ほかの話にする。動画の再生の不具合・台本の話・選択の返事（「Aで」）は、編集への指摘でなければほかの話。
   作る前の指示・参考（参考動画やサムネの見本を渡して「これを参考に」、「こういう編集にしたい」）は `--direction <id …>`。その動画を作る前に実物を見て、言われた範囲（サムネ・字幕・テンポなど）を合わせる。案件のテイストとして残すのは、その案件の次の動画にも効く所だけで、その1本の計画は案件の作業フォルダに置く（下の「最初に、その版の直しと、次からの決まりを分ける」）。最初の動画を渡す時は、それより前の本人の言葉も全部 pending に出る。
3. 記録すると、通知を出さない学習の仕事が裏で起きる。部屋の担当は待たずに動画を渡してよい。この記録を本人への返事に書かない。

編集した動画（30秒以上）を貼るターンは、手順書を読んだか・発言を全部記録したかを、終わる時に関所（hook_video_feedback_gate.py）が確かめる。

エディターの「ダンと制作」の部屋では、動画をチャットに貼らずにタイムラインを直すので、関所は止めない。代わりにターンの終わりに裏の仕分け（`video_learning.py sweep`）が、本人の言葉を指摘・作る前の指示・ほかの話に分けて記録する。通話で話した言葉（部屋の会話に 🎙 付きで残る）も同じく拾われる。

## 学習の仕事がすること

証拠: `python /Users/mikihonda/done/scripts/video_learning.py evidence --job <ID> --output <JSON>`。指摘の全文、部屋の担当が当てはめた所（applied）、前の学習の結果が入る。

### 最初に、その版の直しと、次からの決まりを分ける

指摘は全部、まず**その版の直し**。部屋の担当がもう直していて、直した中身は組み立て（タイムライン・組み立ての記録）に残っている。次の版はそこから作るので、手順書のどの層にも書かなくてよい。「沖縄に着いた絵を4秒以上見せる」「中性脂肪の行にマーカーを引かない」「鼻炎の YouTube の映像は1回だけ」は、どれもその場面への直しで、手順書の決まりではない（2026-11-12 本人「特定の動画の特定のシーンにおいて適用されるべきことで、中村さんの動画全体でそうすべきという内容では無い」）。

手順書に書くのは、その指摘の裏にある**判断の誤り**だけ。決まりの候補ができたら、次の2つを確かめる。

1. **場面の中身を消しても通るか。** 決まりの文から、その場面の話題・固有名・その場面の台詞・版・時刻を消して読む。意味が通らないなら、それは場面の直し。例: 「沖縄に着いた絵を4秒以上」から沖縄を消すと「絵を4秒以上」になり、なぜ4秒なのかが残らない。裏の判断は「出す物は、読める長さで出すか、出さない」で、こちらは中身を消しても通る。
2. **次の別の場面で判断が変わるか。** その決まりがあると、まだ作っていない場面のどこで、何の判断が変わるかを1つ具体に挙げる。案件の決まりなら同じ案件の別の話題・別の動画で、本文なら別の案件で挙げる。挙げられなければ決まりにしない。

取り出した判断が、もう上の層の決まり（本文や案件の決まり）にあるなら、場面の直しは書き足さない。その決まりがなぜ効かなかったかを考える（下の「指摘を決まりにする」の5）。場面は、決まりの例として1つ添えるのはよいが、決まりそのものにしない。

案件の決まりを開いた時、前からある行に場面の直し（版・時刻・その場面の台詞を名指す物）が残っていたら、同じ2つの確かめで見直し、場面の直しなら外し、中に次の動画にも効くテイストが埋まっていれば、それだけを決まりの形で残す。

決まりにも直しにもならない物の行き先:
- その1本の動画の計画（話に出る物と見せる物の表、場面ごとに出す絵、章の札の文言）→ 案件の作業フォルダの計画。手順書には書かない。
- まだ終わっていない作業（お客さんに頼む素材、届いたら差し替える所）→ 案件の作業フォルダの残りの作業と、部屋の待ち仕事。手順書には書かない。

### 指摘をどの層に置くか

置き場所は3つある。上で「次からの決まり」になった物だけを、まず一番狭い層に置き、上の層へは条件を満たした物だけを上げる。

| 層 | ファイル | 置く物 |
|---|---|---|
| — | （手順書に書かない） | その版の直し・その1本の計画・残りの作業（上の節）。変更記録の「場面の直し」にだけ残す |
| 案件 | references/<案件>.md（中村さん = nakamura-line-gift.md、ポルノアンチ = pornanti-line-gift.md） | その案件の次の動画にも効くテイスト。字幕の色・書体・大きさ、効果音の種類と大きさ、寄りの頻度と寄り方、BGM の曲調、配置、演出の手法（どの種類の場面で使うか）、書き出しの形 |
| 型の共通 | SKILL.md（話す人と実物で見せる動画） | どの案件でも通じる判断。次の2つのどちらかに当たる物だけ |

本文（SKILL.md）へ上げてよいのは:
- 同じ判断の誤りが、2つ以上の別の案件で起きた物。例: 同じ素材の使い回し（ポルノアンチと中村さん）。
- 見る人の理解に関わる理由が、テイストに依らない物。例: 実物の素材を先にする、同じ素材を繰り返さない、画面の文字が見る人からどう読まれるか、絵を言葉の前に出さない、証拠を「たまたま」に見せない。

テイスト（字幕の色・書体・効果音の種類・寄りの頻度・BGM の曲調・絵を画面のどちらに置くか・白黒にする演出など）は、2つの案件で同じでも案件の側に残す。本文には「それは案件の決まりで決まる」とだけ書く。迷ったら案件の側に置く（後から上げるのは簡単で、上げた物を別の案件から消すのは難しい）。

### 指摘を決まりにする

指摘ごとに、次の順で考える。

1. **見る人に何が起きていたか**を1文で言う。例: 「中村さんのYouTube」という札は、本人が出ている動画の中では本人の言葉として読まれ、本人が自分を「さん」付けで呼んでいるように見える。
2. **判断のどこを誤ったか**を言う。例: 札を、作る側から見た説明（誰の素材か）で書いていて、見る人からどう読まれるかを確かめていなかった。
3. **置く層を決める**（上の表）。理由を1文で書く。例: 「見る人の理解の話で、テイストに依らない。新アタックの『（デモ）』の注記と同じ誤り」→ 本文。「イラストを画面の左に置く」→ 配置の好みなので中村さんの案件。
4. 本文に上げる物は、**別の動画でも同じ誤りが起きる形**にする。例: 「画面の文字は、誰の声として読まれるかを確かめる」。料理の動画で自分のレシピに「〇〇さんのレシピ」と出す時も同じ。
5. 既にある決まりで足りるなら足さない。その決まりがなぜ効かなかったか（読まれていない・書き方が抽象的・例が無い・別の決まりと食い違う）を直す。
6. 本人の言葉を写すだけにしない。本文の決まりは「何をするか」「なぜか（見る人に起きること）」「別の題材での例」の3つで書く。決まりの羅列で長くしない。似た決まりはまとめる。案件の決まりは、作る人がそのまま使える具体（書体名・音の名前・dB・どの種類の場面で使うか）で書く。場面の時刻や版は、決まりの文に入れない（入れたくなったら、それは場面の直し）。

本人の理由が書かれていない指摘は、推測した理由（inferred）として扱い、書かれた理由（explicit）と分ける。

### 候補を試してから入れる

1. 独立した作業場所で直す: `python /Users/mikihonda/done/scripts/work.py new <名前>`。手を入れる前に今の手順書を写しておく（旧版）。
2. 法則を取り出していない動画で比べる。同じ依頼（「この版を本人に見せる前に見直して、直す所と直し方を書け」など）を、旧版の手順書を読む担当と候補版を読む担当に別々に出す。材料は、別の案件の動画か、同じ動画のまだ指摘されていない区間。手順書の場所の名前で版が分からないようにする。
3. 判定は、どちらの版か伏せた担当にさせる。物差しは「本人が後で言いそうな所を、先に拾えているか」「本人が決めた条件を壊していないか」「頼まれていない加工を足していないか」。本人の後の指摘が分かっている動画なら、それを答えにして点を付ける。答えに使ってよいのは本人が後で言った言葉だけで、部屋の担当がこの指摘から作った版（指摘を受けて外した絵の一覧など）は答えにしない。指摘を受けた場面そのものを比べの材料にしない。どちらも、場面の直しを決まりとして書いた版が勝ってしまう。
   判定の担当には、候補版で足した決まりも1つずつ読ませ、「場面の中身を消しても通るか」「次の別の場面で判断が変わるか」（上の節）に当たらない物があれば、その版の負けにする。
   比べる動画の1本は、指摘を受けた案件とは別の案件にする。そこへ指摘を受けた案件のテイスト（書体・効果音・寄りの頻度・演出）が持ち込まれていたら、その版の負け。
4. 候補版が勝たなければ、直してもう一度比べるか、deferred にする。差が出ない時に無理に決まりを増やさない。
5. 勝ったら、sources/generalization-log.md にこの仕事の id を書いた項目を足し（下の形）、`work.py save` → `work.py test` → `work.py ship`。GitHub は人の速さで使う。認証・権限で断られたら繰り返さず deferred にする。

変更記録の形:
```
## <日付> <何を直したか>
- 種類: 指摘の学習（仕事 <id>）
- 変更するファイル:
- 具体の指摘: 本人の言葉と、どの動画のどの版のどこか
- 見る人に起きていたこと:
- 場面の直し（手順書に書かなかった物）: 指摘ごとに、その版で何を直したかと、決まりにしなかった理由（裏の判断が既にある決まりに入る・中身を消すと通らない など）
- 置いた層となぜその層か: 指摘ごとに「案件（<ファイル>）／本文」と理由
- 決まり:
- 別の題材での例:
- 足さなかった物と理由:
- 比べた物: 依頼・旧版・候補版・判定のファイルと結果
```

### 完了の報告

`python /Users/mikihonda/done/scripts/video_learning.py complete --job <ID> --report <JSON>`。文章だけで終えても完了にならない。本文（SKILL.md）を直した時は、別の案件の動画で比べた項目（`other_case: true`）が要る。

```json
{
  "outcome": "promoted",
  "feedback_ids": ["この仕事の指摘の id を全部"],
  "reason": "何が良くなり、何を保ったか。比べ方の限界も",
  "lessons": [{
    "rule": "何をするか",
    "why": "見る人に何が起きるか",
    "layer": "case（案件の決まり）か skill（本文）",
    "layer_reason": "その層に置いた理由（2つ以上の案件で起きた・理解に関わりテイストに依らない・テイストなので案件側 など）",
    "basis": "explicit か inferred",
    "evidence_ids": ["根拠の指摘の id"],
    "elsewhere": "この決まりで判断が変わる、まだ作っていない別の場面（案件の決まりなら同じ案件の別の話題・別の動画、本文なら別の案件）と、どう変わるか"
  }],
  "scene_fixes": [{
    "feedback_id": "指摘の id",
    "fix": "その版で直したこと（例: 沖縄に着いた絵を4秒見せる）",
    "why_not_rule": "決まりにしなかった理由（例: 裏の判断「読める長さで出すか出さない」は本文にある）"
  }],
  "evaluations": [{
    "held_out": true,
    "request_path": "/絶対パス/依頼.md",
    "old_output_path": "/絶対パス/旧版の出力.md",
    "new_output_path": "/絶対パス/候補版の出力.md",
    "winner": "candidate",
    "other_case": false,
    "reason": "具体的な比較の理由"
  }],
  "repository": "/作業場所",
  "commit": "保存したコミットID",
  "skill_paths": [".claude/skills/talking-demo-editing/SKILL.md", ".claude/skills/talking-demo-editing/sources/generalization-log.md"]
}
```

`scene_fixes` は、指摘のうち決まりにしなかった物を全部書く（無ければ空の並び）。案件の決まり（references/<案件>.md）だけを書き足し、SKILL.md の判断の決まりを変えなかった時は outcome=case_only（比べは要らない。commit・skill_paths・変更記録は要る）。complete は、手順書に足した行に版（v14 など）や時刻（3:05 など）が入っていると通さない。保留は outcome=deferred（次に何が分かれば決められるかを reason に）。書き足す物が何も無い（すでに決まりがあり効いている）なら no_lesson。どれも feedback_ids と reason は要る。
