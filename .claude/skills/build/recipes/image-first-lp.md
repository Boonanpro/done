# T0 画像ファーストLP（LP・広告LPの既定方式）

GPT Image 2 でLPデザインを**画像として生成**し、操作が必要な箇所（入力欄・ボタン）だけを
実HTMLで重ねる方式。コードでデザインを組み立てない。

2026-08-03 に置く床暖房LPで通し検証済み。従来のコード方式より速く、デザイン品質も高い
（AIの平均的なHTML出力ではなく、画像モデルのデザイン能力をそのまま使えるため）。

## いつ使う / 使わない

| 使う（既定） | 使わない（従来のコード方式 T1〜T4） |
|---|---|
| 広告LP・ドライテストLP・キャンペーンページ | 多ページ企業HP（kittoku型） |
| 縦スクロール1枚もの | SEO・検索流入が主目的のサイト |
| スマホユーザーが主対象 | 頻繁な文言更新を客が自分で行うサイト |
| | ダッシュボード・管理画面・機能ページ |

**この方式ではリファレンス収集(HM5)・自己採点ループ(criteria.md)は不要**。
デザイン品質は画像モデル側が担保する。代わりに後述の「文字QA」を必ず行う。

## 制約（先に知っておく）

- 生成は **OpenAI API直 `scripts/gpt_image.py` が正規経路**（2026-08-11一本化。
  品質はHiggsfield経由と同等を実証済みで、速くて安い。Higgsfieldは動画・Soul・
  キャラ参照専用に温存する）
- サイズは自由指定だが**縦横比3:1以内・最長辺3840px**。LP全体は入らないので
  タイル分割で作る（カンプは 1280×3840 まで1枚にできる）
- タイルの基準幅は1520px（スマホ幅の約3.9倍で拡大にも耐える）。高さはスライスに合わせる
- Inspector編集は使えない。文言修正は「タイル再生成→領域合成」で行う（後述）
- テキスト選択・コピー不可。SEOはalt属性のみ（広告LPでは実害なし）

## 手順

### 1. カンプ — まずLP全景を「1枚出し」で作る

いきなりタイルを作らない。**最初にLP全体を1枚の縦長画像（1280×3840＝3:1）
として生成し、構成・配色・リズムの設計をモデル自身に1枚の中でやらせる**。
1枚出しの方が全体バランスが良い — タイル逐次生成ではページ全体の視覚設計が
失われるため、カンプで大域設計を先に確定する。
9:16に押し込むと全景が縦に潰れ、清書時に「配置し直し」の誘惑（＝設計破壊）が
生まれるので、カンプは必ず3:1の縦長で作る。

- プロンプトに入れるのは**ユーザーの要望そのものだけ**:
  ①何のページか ②何を伝えたいか ③ユーザーが挙げた情報（価格・特徴・
  ターゲット等）④実際の写真・画像素材があれば `--image` で渡す
- **「スマートフォンの縦画面で読まれる縦長LP」という媒体情報は必ず入れる**
  （デザイン指示ではなく要望情報の一部。漏れるとPC向けの横組みで出てくる）
- **表示テンポの標準要望（ユーザー既定 2026-08-12）**: プロンプトに
  「スマホの1画面分（およそ画面幅の2倍の高さ）に、伝えたいことが1つずつ
  入るテンポで構成してください。1画面に複数のメッセージが同時に映らないように」
  を必ず含める。スクロール中のどの瞬間も主役が1つだと理解が楽になるため。
  これは読まれ方の要件であり、各画面の見た目・密度・部品の選択は
  引き続きモデルに任せる（レイアウトの処方を足さない）
- 作り直しで既存カンプ・採用案の画像を参照に渡すと**元のレイアウトに強く
  引きずられる**（2026-08-12 実測: 素の参照＋「スマホ用にして」は2回連続で
  横並びが残った）。レイアウトを変えたい作り直しは次の2択:
  (a) 参照を渡さず情報だけで作る
  (b) 渡すなら「この画像からは配色と書体だけを引き継ぐ。レイアウトは新しく」と
  **引き継ぐ範囲を明示**する（3回目にこれで成功した実績あり）
- **デザインの方向性を一切足さない**（配色・書体・写真かイラストか・トーン・
  「モダンに」等の形容も含む）。デザイン判断と方向転換の指示はユーザーがする
- **カンプ承認チェックポイント（必須）**: カンプができたら**画像をチャットに
  添付してユーザーに見せ、承認または修正指示をもらってから**清書に進む。
  勝手に清書まで進まない。理由: 直しはカンプ段階なら1回数円・数十秒だが、
  タイル化後のやり直しは清書全部が無駄になる（2026-08-12 ユーザー指示）
- ダンの仕事は**要望と素材の伝え漏れを無くすこと**だけ。デザインの良し悪しの
  判断と方向転換はユーザーがする。指示（情報の補足・デザイン変更）があれば、
  その指示だけ反映して作り直し、再度見せる
- 過去案件の画像を参照に渡さない（単調化するため）
- カンプは設計図。細部の文字は化けていてよく、全体の見た目だけを見る。
  **高画質・高解像度にする必要はない**（本番の画質はタイル清書側で作るため、
  低い品質設定で生成してよい。ユーザーがChatGPT等で作った縦長画像を
  そのままカンプとして受け取るのも可）

### 2. タイル清書 — 採用カンプの該当区間を参照に高解像度で再現

採用カンプを**要素の切れ目で**縦に切り出す（文字や部品を跨ぐ位置で切らない。
枚数は決めない — 内容の切れ目の数で自然に決まる）。各区間を `--image` で渡して
「清書」させる。**清書プロンプトは次の定型文に固定**:

```
（カンプの該当区間を --image で添付）
参照画像のデザイン・レイアウト・配色をそのまま、細部まで高解像度で綺麗に
清書してください。要素の追加・削除・並べ替えはしないこと。
文言は以下の通り一言一句正確に:
...
日本語の文字はすべて正確に、誤字なく描くこと。
```

⚠️ **この定型文に、文言と入力欄・ボタンの配置指定以外を足すことを禁止。**
特にレイアウト・配置・余白・背景・並べ方の指示を足してはいけない
（2026-08-11 実例: 「縦長の画面いっぱいにゆったり配置し直せ」「左右に2つ以上
並べるな」を足した清書が、承認済みカンプの設計を壊してスカスカのLPになった。
カンプの潰れは清書で補正せず、カンプを3:1で作ることで解決する）。

**デザイン上のルールは設けない**。残すのは以下だけ:

- タイルの生成サイズは**スライスと同じ縦横比**にする（両辺16の倍数に丸める。
  例: スライスが1280×970なら生成は1520×1152）
- **生成後のcropは禁止**。Webは縦に積むだけなのでタイルの高さは揃わなくてよい。
  切り貼りで整えず、生成したままの画像を並べる

- 清書プロンプトでは文言を確定させて渡す（でないと手順4の文字QAの照合基準が
  ない）。コピーはユーザーの伝えたい情報から起こしてよいが、**間違えられない値
  （価格・電話番号・住所・固有名詞）はユーザーの挙げた値をそのまま使う**
- 入力欄・ボタンは「どこに・何と書いたものを置くか」だけ指定して画像内に
  描き込ませる（**見た目は指定しない**）。座標は materialize の自動検出に掛け、
  検出に失敗したら画像を目視して手動で座標を書く

### 3. 生成コマンド

```bash
# カンプ（全景1枚出し。ユーザーが枚数を指定しない限り1案。1280x3840まで縦長可）
cat comp.txt | python scripts/gpt_image.py --size 1280x3840 --quality low --out comp.png --json

# タイル清書（採用カンプの該当区間を --image で渡す。全タイル並列OK。
# --size は毎回スライスと同じ縦横比・16の倍数で計算する）
cat tile2_prompt.txt | python scripts/gpt_image.py --image comp_slice_2.png \
  --size 1520x1152 --quality low --out t2.png --json
```

**品質は `--quality low` が既定**（2026-08-11 実測: 同一タイルを low/medium/high で
生成して等倍比較し、文字・写真とも視認差なし。low≈$0.02/枚・15〜60秒）。
細かい図表・アイコン密集タイルで描き込みが崩れた時だけ、そのタイルを
medium → high と上げて再生成する。解像度（--size）は下げない。

- 全タイル並列実行してよい（各タイルは自分のカンプ区間を参照するので互いに独立）
- 1枚15〜60秒。401やquotaエラーは OPENAI_API_KEY と Billing 残高を確認
  （チャージはユーザーに依頼する）

**⚠️ 生成完了までターンを終えないこと。**「生成中です、あと数分」と報告して
ターンを終えると、バックグラウンドの生成プロセスはターン終了と同時に死に、
完了通知も次ターンに届かない（2026-08-03 実測: 並列7ジョブが全滅）。
並列化はシェルの `( ... --wait ... ) & ... wait` で**同一コマンド内で完了まで待つ**。
完了→文字QA→具現化→検証→URL報告までを1ターンで完走する。

### 4. 文字QA（必須）

各タイルを Read で表示し、**プロンプトの指定文言と1文字ずつ照合**する。
誤字・脱字・勝手な改変があればそのタイルだけ再生成。
（実測: 9タイル生成して誤字ゼロだったが、保証はないので必ず見る）

### 5. 具現化 — 座標検出とページ生成

```bash
python scripts/lp_image_materialize.py \
  --images t1.png t2.png t3.png --slug <slug> \
  --out-json coords.json --out-page page.tsx
```

- ボタン（ベタ塗り横長・彩度高）と入力欄（白い横長・文字なし・ボタンの直上）を
  色検出して座標JSON + page.tsx 雛形を出力する
- 検出結果は**必ず目視確認**（雛形ページの「操作領域を表示」トグルで赤枠表示）
- 雛形の TODO（送信先scope・LINE URL・ボタンの遷移先）を案件に合わせて埋める
- 画像は `frontend/public/scratch/<slug>/`（試作）または
  `frontend/public/artifacts/<slug>/`（納品）に置く

ページ側の必須事項:
- `/scratch` 配下は専用 layout.tsx で html/body のスクロール解放
  （globals.css の overflow:hidden 対策。`/artifacts` 配下は既存 layout が解決済み）
- ルート layout が `maximumScale: 1` なので、viewport export で
  `maximumScale: 5, userScalable: true` を上書き（ピンチ拡大できないと画質確認不能）
- エラーメッセージ等の後付けUIは**不透明背景の帯**にする（背後の描き込み文字と被るため）

### 6. 修正 — タイル再生成 → 領域合成

GPT Image 2 の参照編集は**全体を微妙に描き直す**（実測: 文言1つの修正でタイル全体の
約12%が変化）。そのまま差し替えず、**変更したい領域だけを元画像に合成**して
領域外の完全不変を保証する:

```bash
# 1. 該当タイルを参照にして修正版を生成
echo "添付画像の◯◯を「◯◯」に変更。それ以外は一切変更しない" | \
  python scripts/gpt_image.py --image t1.png --size 1520x2688 --quality low --out t1_edit.png

# 2. 変更領域だけ合成（--region 推奨。場所が不明なら --auto + 目視確認）
python scripts/lp_image_patch.py --original t1.png --edited t1_edit.png \
  --region <x0,y0,x1,y1> --out t1_v2.png
```

- `--region` の座標は coords.json（materialize出力）か画像目視から取る
- 出力の `changed OUTSIDE region: 0.0000%` を必ず確認
- レイアウト自体を変える修正（要素の追加・移動）は合成不可。タイルごと作り直し、
  文字QAをやり直す
- 貼った矩形が薄い帯として見えることがある。生成側の背景トーンが元と2〜4階調
  ずれるためで、広いベタ面だと段差になる。枠のすぐ内側のリングで色差の中央値を
  取って貼る側に足すと消える（実測 段差 2〜4 → 0.4）

> プロンプトは必ず**標準入力**で渡す（コマンド引数に改行入り文字列を渡すと
> フラグが壊れる事故の元。`gpt_image.py` はそのための設計）。
> `--mask` で修正領域をマスク指定することもできるが、モデルはマスク形状に
> 完全には従わないため、**領域外不変の保証は従来どおりこの手順の合成で行う**。

### 7. 検証

Playwright で: 表示200・操作領域の位置ズレ（赤枠トグル）・入力→送信→API 200・
CTAスクロール・モバイルviewportスクショ。実機URL（LAN IP）をユーザーに渡す。

## Higgsfield fallback（OpenAI APIが使えない時のみ）

同じ GPT Image 2 を higgsfield CLI 経由でも生成できる:
`cat p.txt | higgsfield generate create gpt_image_2 --aspect_ratio 9:16 --resolution 2k --quality low --wait --json`
⚠️ プロンプトは必ず標準入力（`--prompt` 引数は改行でフラグが壊れる）。
`result_url` は明示的に読む（再帰URL探索は入力画像を掴む）。
