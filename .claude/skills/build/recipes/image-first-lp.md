# T0 画像ファーストLP（LP・広告LPの既定方式）

GPT Image 2 でLPデザインを**画像として生成**し、操作が必要な箇所（入力欄・ボタン）だけを
実HTMLで重ねる方式。コードでデザインを組み立てない。

2026-08-03 に置く床暖房LPで通し検証済み。従来のコード方式より速く、デザイン品質も高い
（AIの平均的なHTML出力ではなく、画像モデルのデザイン能力をそのまま使えるため）。

## いつ使う / 使わない

| 使う（既定） | 使わない（従来のコード方式 T1〜T4） |
|---|---|
| 広告LP・ドライテストLP・キャンペーンページ | 多ページ企業HP（kittoku型） |
| 縦スクロール1枚もの | SEO・検索流入が主目的のサイト |
| スマホユーザーが主対象 | 頻繁な文言更新を客が自分で行うサイト |
| | ダッシュボード・管理画面・機能ページ |

**この方式ではリファレンス収集(HM5)・自己採点ループ(criteria.md)は不要**。
デザイン品質は画像モデル側が担保する。代わりに後述の「文字QA」を必ず行う。

## 制約（先に知っておく）

- 生成は **OpenAI API直 `scripts/gpt_image.py` が正規経路**（2026-08-11一本化。
  品質はHiggsfield経由と同等を実証済みで、速くて安い。Higgsfieldは動画・Soul・
  キャラ参照専用に温存する）
- サイズは自由指定だが**縦横比3:1以内・最長辺3840px**。カンプは1280×3840を
  1枚として、**2〜4セクションずつチェーン**で必要枚数作る（手順1参照）
- タイルの基準幅は1520px（スマホ幅の約3.9倍で拡大にも耐える）。高さはスライスに合わせる
- Inspector編集は使えない。文言修正は「タイル再生成→領域合成」で行う（後述）
- テキスト選択・コピー不可。SEOはalt属性のみ（広告LPでは実害なし）

## 入口の判定 — 新規デザインか、既存LPの修正か

- **新規制作、またはレイアウトから変えるデザイン変更** → 手順1のカンプから始める。
  カンプの目的は「どの話をどの順で見せるか」の確認ではなく、**デザインの設計図**
  （配色・レイアウト・雰囲気・部品を安く確定し、清書が忠実に再現するための原本）。
  構成の合意（セクション表など）はカンプの代わりにならない
- **既存LPの修正**（文言直し・画像差し替え・色やトーンの調整など、出来ている
  ページを直す作業）→ **カンプは作り直さない**。手順6の修正ルーティングで行う。
  「カンプを作る＝全部描き直し」ではない — 部分修正なら残す箇所は1画素も変わらない

## 手順

### 1. カンプ — 1枚に2〜4セクションずつ、チェーンで作る

いきなりタイルを作らない。まずカンプ（設計図）を作るが、**LP全景を1枚に
押し込まない**こと。カンプ1枚（1280×3840）には**2〜4セクションだけ**を
割り当て、必要な枚数をチェーンして全景にする。

なぜ1枚2〜4セクションか（2026-08-14 計測で確定）:
- 全景を1枚に押し込むと各セクションが実寸の1/3以下に圧縮され、
  そのまま清書すると**4画面しかない読めないLP**になる（実測: 20セクション
  ≈4.2画面・文字極小）。後から伸ばす方式は文字が縦に歪み不合格（文字縦横比
  実測1.7〜2.0。正常は1.1〜1.4。文言での抑止は幾何圧力に勝てない)
- 1枚2〜3セクションなら**最初からスマホ実寸の縦横比で描かれ**、文字の形も
  大きさも正常（実測1.1）。さらに各セクションに空間があるため、アイコン行・
  チェックリスト・図解などが自然に生まれ、**紙芝居化も同時に解消**する
- 商用実例の実測とも一致（maro17: ページ全長=スマホ10.6画面・1画面あたり
  約1.4セクション）

チェーンのやり方: プロンプトに「この画像に入れるのは次の◯個のセクション
だけです。長いページの一部分で、続きは別の画像で作ります。スマートフォンの
画面でそのまま表示される実寸のつもりで、ゆとりのある大きさで描いてください」
と書く。**2枚目以降は参照を2枚渡す**: `--image <1枚目=アンカー> --image <直前の枚>`
の順で渡し、「1枚目の添付画像は、このLPの冒頭（デザインの基準）です。配色・書体・
デザインの雰囲気は常にこれに揃えてください。2枚目の添付画像は直前の部分です。
その続きとして、ページの流れが途切れないようにしてください」と指示する。
理由: 隣だけの参照は「コピーのコピー」でズレが枚数に比例して溜まる。アンカー方式は
何枚目でも原本から1ホップなので構造的に溜まらない（2026-08-18 6枚チェーン比較で
副作用なし・終盤の色保持が改善。2026-08-12の「全タイル1枚目参照で一貫性問題なし」の
実績とも一致）。分割位置は内容の転換点に置く。参照chainのため逐次実行になる。

**割り当ては均等に刻まない。ただし1枚あたり2〜4場面の範囲で**: 主役場面
（ヒーロー・締めCTA等）は2場面/枚、説明の密な場面は3〜4場面/枚、と場面の
重みで枚ごとに変える。全部を同じ刻みにすると、全セクションが同じ大きさの
カードの行列になる単調が出る（2026-08-15 実例）。
**1枚を1場面に独占させない** — キャンバスは常にスマホ約2.1画面分なので、
1場面独占はそのセクションが約2画面の巨大サイズになる（実測でユーザー不合格）。
2場面/枚なら最大でも約1画面に機械的に収まる。
**セクションの上限サイズ≈スマホ1画面前後（ユーザー既定 2026-08-15）**。

- プロンプトに入れるのは**ユーザーの要望そのものだけ**:
  ①何のページか ②何を伝えたいか ③ユーザーが挙げた情報（価格・特徴・
  ターゲット等）④実際の写真・画像素材があれば `--image` で渡す
- **「スマートフォンの縦画面で読まれる縦長LP」という媒体情報は必ず入れる**
  （デザイン指示ではなく要望情報の一部。漏れるとPC向けの横組みで出てくる）
- **文章量の標準要望（ユーザー既定 2026-08-14・A/B検証の勝者文言）**: プロンプトに
  「文章は最小限にしてください。読まなくても、見ただけでメッセージが伝わる
  ビジュアル中心の誌面にしてください。しっかり文章で伝えるべき箇所だけ、
  例外的に文章を使ってください」を必ず含める
  （短縮版「できるだけビジュアルで」は逆に文字が増えた実測あり。文言を変えない）
- **事実の作文禁止（必須）**: プロンプトに「実在しない数字・統計・出典・実績を
  描かないでください」を必ず含める（実例: 架空のED有病率グラフ、実在しない
  論文引用まで描かれた。数字・実績はユーザーが提供したものだけ使う）
- 「セクション番号や連番のラベルは表示しない」も必ず含める（章番号が
  そのまま描かれる事故の抑止）
- **参照LPフロー（任意）**: テイストや情報の見せ方を変えたい時は、sankou等の
  ギャラリーから候補を2〜3点引いて**ユーザーに選んでもらい**、選ばれた1点を
  「情報の見せ方・レイアウトの密度感・読みやすさを参考に。配色・題材・文言は
  引き継がない」の限定つきで `--image` 参照する（限定すればテイストの
  丸写しにはならないことを実証済み）。ダンが勝手に参照を選んで渡さない
- **ユーザーの文章は既定で「意図」として扱う**: 要望の文を鉤括弧つきで
  プロンプトに貼ると、モデルはそれを逐語コピーとして描く（「そのまま使うな」
  というメタ注記より、貼られた文の方が強い — 2026-08-13 実測）。
  伝えたいことは内容の説明に言い換えて渡し、「文言は自由に作ってよい」と
  添える。ユーザーが一言一句を指定した場合だけ【文言指定】として逐語で渡す。
  判定の目安: 短いキャッチコピー（見出しになる決め台詞）はそのまま、
  説明的な文は言い換え。判別を誤ってもカンプ承認時に安く直せる
- 作り直しで既存カンプ・採用案の画像を参照に渡すと**元のレイアウトに強く
  引きずられる**（2026-08-12 実測: 素の参照＋「スマホ用にして」は2回連続で
  横並びが残った）。レイアウトを変えたい作り直しは次の2択:
  (a) 参照を渡さず情報だけで作る
  (b) 渡すなら「この画像からは配色と書体だけを引き継ぐ。レイアウトは新しく」と
  **引き継ぐ範囲を明示**する（3回目にこれで成功した実績あり）
- **デザインの方向性を一切足さない**（配色・書体・写真かイラストか・トーン・
  「モダンに」等の形容も含む）。デザイン判断と方向転換の指示はユーザーがする
- **カンプ承認チェックポイント（必須）**: 全カンプができたら**疑似LPプレビュー**を
  作ってURLをチャットで渡し、スマホ実寸のスクロールで確認してもらう。縦長の
  全景画像の添付は補助にとどめる（細くなりすぎて細部が見えない）。承認または
  修正指示をもらってから清書に進む。確認は1回でよい。

  **プレビューの作り方（uploads配信・どのデバイスでも開ける）**:
  1. カンプ画像を `D:/done/uploads/` に置く（幅900px程度に縮小してよい）
  2. 単一HTML（1ファイル完結）を同じく uploads に置く: `<meta viewport>` で
     `maximum-scale=5, user-scalable=yes`、本文は max-width 430px の中央カラムに
     画像を縦積み、各画像は原寸PNGへの `<a target="_blank">` で包む
     （幅100%だけだとPCでブラウザズームしても窓に再フィットして拡大にならない）
  3. URLは `https://<アプリ公開ドメイン>/api/v1/files/<slug>_preview.html`。
     **渡す前に必ず `curl` で 200 と content-type: text/html を確認**
  - ⚠️ `/scratch` ページ＋Tailscale IP方式は使わない（本番ドメインに/scratchは
    無く404、TailscaleのオンをユーザーにさせるのはNG — 2026-08-15 feedback）。
    uploads方式はアプリの通常公開経路なのでVPN不要
  勝手に清書まで進まない。理由: 直しはカンプ段階なら1回数円・数十秒だが、
  タイル化後のやり直しは清書全部が無駄になる（2026-08-12 ユーザー指示）
- ダンの仕事は**要望と素材の伝え漏れを無くすこと**だけ。デザインの良し悪しの
  判断と方向転換はユーザーがする。指示（情報の補足・デザイン変更）があれば、
  その指示だけ反映して作り直し、再度見せる
- 過去案件の画像を参照に渡さない（単調化するため）
- カンプは設計図。細部の文字は化けていてよく、全体の見た目だけを見る。
  **高画質・高解像度にする必要はない**（本番の画質はタイル清書側で作るため、
  低い品質設定で生成してよい。ユーザーがChatGPT等で作った縦長画像を
  そのままカンプとして受け取るのも可）

### 2. タイル清書 — 採用カンプの該当区間を参照に高解像度で再現

採用カンプを**要素の切れ目で**縦に切り出す（文字や部品を跨ぐ位置で切らない。
枚数は決めない — 内容の切れ目の数で自然に決まる）。各区間を `--image` で渡して
「清書」させる。**清書プロンプトは次の定型文に固定**:

```
（カンプの該当区間を --image で添付）
参照画像のデザイン・レイアウト・配色をそのまま、細部まで高解像度で綺麗に
清書してください。要素の追加・削除・並べ替えはしないこと。
文言は以下の通り一言一句正確に:
...
日本語の文字はすべて正確に、誤字なく描くこと。
```

⚠️ **この定型文に、文言と入力欄・ボタンの配置指定以外を足すことを禁止。**
特にレイアウト・配置・余白・背景・並べ方の指示を足してはいけない
（2026-08-11 実例: 「縦長の画面いっぱいにゆったり配置し直せ」「左右に2つ以上
並べるな」を足した清書が、承認済みカンプの設計を壊してスカスカのLPになった。
スケールの問題は清書で補正せず、カンプの2〜4セクション/枚方式で解決する）。

**デザイン上のルールは設けない**。残すのは以下だけ:

- タイルの生成サイズは**スライスと同じ縦横比**にする（両辺16の倍数に丸める。
  例: スライスが1280×970なら生成は1520×1152）
- **生成後のcropは禁止**。Webは縦に積むだけなのでタイルの高さは揃わなくてよい。
  切り貼りで整えず、生成したままの画像を並べる

- 清書プロンプトでは文言を確定させて渡す（でないと手順4の文字QAの照合基準が
  ない）。コピーはユーザーの伝えたい情報から起こしてよいが、**間違えられない値
  （価格・電話番号・住所・固有名詞）はユーザーの挙げた値をそのまま使う**
- 入力欄・ボタンは「どこに・何と書いたものを置くか」だけ指定して画像内に
  描き込ませる（**見た目は指定しない**）。座標は materialize の自動検出に掛け、
  検出に失敗したら画像を目視して手動で座標を書く

### 3. 生成コマンド

```bash
# カンプ（1枚に2〜4セクション。2枚目以降は前の枚を --image で参照してチェーン）
cat comp.txt | python scripts/gpt_image.py --size 1280x3840 --quality low --out comp.png --json

# タイル清書（採用カンプの該当区間を --image で渡す。全タイル並列OK。
# --size は毎回スライスと同じ縦横比・16の倍数で計算する）
cat tile2_prompt.txt | python scripts/gpt_image.py --image comp_slice_2.png \
  --size 1520x1152 --quality low --out t2.png --json
```

**品質は `--quality low` が既定**（2026-08-11 実測: 同一タイルを low/medium/high で
生成して等倍比較し、文字・写真とも視認差なし。low≈$0.02/枚・15〜60秒）。
細かい図表・アイコン密集タイルで描き込みが崩れた時だけ、そのタイルを
medium → high と上げて再生成する。解像度（--size）は下げない。

- 全タイル並列実行してよい（各タイルは自分のカンプ区間を参照するので互いに独立）
- 1枚15〜60秒。401やquotaエラーは OPENAI_API_KEY と Billing 残高を確認
  （チャージはユーザーに依頼する）

**⚠️ 生成完了までターンを終えないこと。**「生成中です、あと数分」と報告して
ターンを終えると、バックグラウンドの生成プロセスはターン終了と同時に死に、
完了通知も次ターンに届かない（2026-08-03 実測: 並列7ジョブが全滅）。
並列化はシェルの `( ... --wait ... ) & ... wait` で**同一コマンド内で完了まで待つ**。
完了→文字QA→具現化→検証→URL報告までを1ターンで完走する。

### 4. 文字QA・スケールQA（必須）

各タイルを Read で表示し、**プロンプトの指定文言と1文字ずつ照合**する。
誤字・脱字・勝手な改変があればそのタイルだけ再生成。
（実測: 9タイル生成して誤字ゼロだったが、保証はないので必ず見る）

あわせて**ページ全長を数値確認**する: 全タイルの合計高さ（幅1520換算）が
おおよそ「セクション数 × 幅の1.3〜1.8倍」に収まっているか。大幅に短ければ
カンプが圧縮されている（4画面LP事故の再発）。目安の根拠は商用実例の実測
（maro17: 全長=幅の22.9倍・スマホ10.6画面・1画面約1.4セクション）。

### 5. 具現化 — 座標検出とページ生成

```bash
python scripts/lp_image_materialize.py \
  --images t1.png t2.png t3.png --slug <slug> \
  --out-json coords.json --out-page page.tsx
```

- ボタン（ベタ塗り横長・彩度高）と入力欄（白い横長・文字なし・ボタンの直上）を
  色検出して座標JSON + page.tsx 雛形を出力する
- 検出結果は**必ず目視確認**（雛形ページの「操作領域を表示」トグルで赤枠表示）
- 雛形の TODO（送信先scope・LINE URL・ボタンの遷移先）を案件に合わせて埋める
- 画像は `frontend/public/scratch/<slug>/`（試作）または
  `frontend/public/artifacts/<slug>/`（納品）に置く

ページ側の必須事項:
- `/scratch` 配下は専用 layout.tsx で html/body のスクロール解放
  （globals.css の overflow:hidden 対策。`/artifacts` 配下は既存 layout が解決済み）
- ルート layout が `maximumScale: 1` なので、viewport export で
  `maximumScale: 5, userScalable: true` を上書き（ピンチ拡大できないと画質確認不能）
- エラーメッセージ等の後付けUIは**不透明背景の帯**にする（背後の描き込み文字と被るため）

### 5b. 実テキスト化 — 文字をチャットから編集可能にする（新規納品の既定工程）

画像LPの文字は画像の一部なので、そのままでは成果物タブの手動編集モードで
文字をつかめない。**新規LPの納品はこの工程まで込みが既定**（ユーザーは
「編集できるようにして」と言わなくても編集できるべき）。既存LPの後付け変換は
求められた時でよい。
`scripts/lp_textify.py` が「文字を画像から消す → 同じ見た目のwebフォント文字
（EditableText）を同じ位置に重ねる」を自動でやり、編集可能ページを生成する。

このツールの契約は「**黙って劣化しない**」: 完全な再現は約束しないが、
再現できていない箇所は必ず検証ゲートに引っかかり、数値と比較画像で表に出る。

```bash
python scripts/lp_textify.py --spec <workdir>/textify_spec.json run
```

spec はツールのdocstring冒頭に書式がある（読んでから書く）。書くのは
**タイルごとの文字ブロック領域(box)と、行ごとの文言の転記**だけ。位置・大きさ・
色・フォント分類は自動検出され、Playwrightで実際に描いて測る較正が入る。

**運用の型（1回で決めず、目視→spec補正→再実行で収束させる）**:

1. spec を書いて実行 → `/preview/<slug>` を開き、元タイルと**並べて拡大比較**する
   （`/preview/` は artifacts ページを未公開のままローカル配信するルート。
   公開前の検証はここで行う）
2. 実行のたびに**検証ゲート**が自動で走る（元タイルと配信ページを文字ブロック
   ごとに機械比較）。結果の読み方:
   - **FAIL（diff≥0.12）= 確実な劣化**（装飾欠落・消し残りゴースト・大ズレ）。
     直すまで不合格。納品不可
   - **WARN（0.035〜0.12）= 機械では白黒つかない帯**。生成された比較画像
     （workdir/verify/）を**全部ズームで目視**し、劣化なしと確認できて初めて合格。
     フォント字形のわずかな違いはここに入る（許容）
   - 検証はdevサーバー必須。開けなかった時は「検証未実施」であり合格ではない
3. FAIL/WARNの原因に応じて spec を補正して再実行:
   - 位置ズレ → `overrides` の `x/y/w/h`（配置だけ動く。消去位置は検出値のまま。
     `w` は文字列の目標幅で、字間は描画実測で `w` に合うよう自動調整される。
     座標は**推測でなく元タイルをnumpyで実測**して書く）
   - 太さ・色 → `wt`（100-900）/ `color`。自動分類は光彩や下地で狂うことがある
   - 元フォントの字幅が広い/狭い（字間を合わせると隙間が不自然）→ `stretch`
     （横スケール。例 1.12。字間でなく字幅で合わせる）
   - チップ・枠の中の文字 → `ebox: [x0,y0,x1,y1]` で消去範囲を明示
     （枠内は面塗り。アイコンは ebox の外に置けば残る）
   - 光彩・影・縁取り・グラデ文字 → region の `halo` / `shadow` / `stroke` /
     `grad`（CSSで再現するので**編集後の文言にも装飾が付いてくる**）
4. 収束したら通常の公開フロー（commit → push → writeback運用は
   CLAUDE.md「クライアント artifact の公開ルール」に従う）。ユーザーへの報告には
   WARNとして目視合格にしたブロックの比較画像を添える（何を許容したかを見せる）

特殊ケースの判断:
- **装飾（光彩・下地・帯）と重なった文字**: `"erase": "generative"`（生成消去）。
  プロンプトは既定で「**グリフだけ消して周囲の光彩・下地は残す**」— 装飾は
  元デザインの一部なので消さず背景側に温存するのが原則（消しすぎてCSSで
  作り直すより、残した実物の上に文字を重ねる方が忠実）。結果はキャッシュされ
  再実行無料。boxは文字の描き込みより広めに取り、最初に決めて動かさない
  （boxやプロンプトを変えるとキャッシュ無効=API課金が再発生）
- **ロゴ・筆文字など道具箱でも再現不能な装飾文字**: `force: "keep"` で絵のまま
  残す（そこだけ編集は従来の部分修正）。ツールの「装飾注意」は過検知が多いので
  判断はゲートの数値と比較画像で行う
- **行内の部分色**（「依存」だけ紫等）: lines のセグメント色に書けば `<span>` で
  再現される（地色はセグメント色の画素を除いて自動検出）。編集するとその行の
  色分けは消える（全体が地色になる）ことは仕様
- **白抜き文字・グロー背景**: フォント太さの密度分類が誤爆しやすい（明朝や
  極太に化ける）。おかしければ `fam`/`wt` を明示する
- **サブブロック間の空きが不均等な段落**（チェックリスト等）: 1つの region だと
  行間が単一値になり位置がドリフトする → **サブブロック単位に region を分ける**。
  行頭アイコン付きの行は `ebox` を文字だけに絞ればアイコンが残る

### 6. 修正 — 指示のルーティングと領域合成（カンプ・タイル共通）

**まずユーザーの修正指示を2種類に振り分ける**:

- **部分修正**（場所や要素を指した指示。「この見出しだけ」「この写真を」等）
  → 指定範囲の外は**1画素も変えない**。下の「再生成→領域合成」で行い、
  `changed OUTSIDE region` がほぼ0%であることを確認してから
  before/after を並べて見せる
- **全体修正**（「もっと◯◯なトーンに」「作り直して」等、全体の変化を求める指示)
  → まるごと再生成してよい（領域合成はしない）
- 曖昧なら**部分修正に倒す**（狭く直すのが安全。足りなければユーザーが
  もう一度言えば広げられるが、余計に変えたものは戻せない）

このルーティングは**カンプの修正にも同じように使う**。カンプ承認時の
「ここだけ直して」にも再生成→領域合成を適用し、指定外を動かさない。

GPT Image 2 の参照編集は**全体を微妙に描き直す**（実測: 文言1つの修正でタイル全体の
約12%が変化）。そのまま差し替えず、**変更したい領域だけを元画像に合成**して
領域外の完全不変を保証する:

```bash
# 1. 該当タイルを参照にして修正版を生成
echo "添付画像の◯◯を「◯◯」に変更。それ以外は一切変更しない" | \
  python scripts/gpt_image.py --image t1.png --size 1520x2688 --quality low --out t1_edit.png

# 2. 変更領域だけ合成（--region 推奨。場所が不明なら --auto + 目視確認）
python scripts/lp_image_patch.py --original t1.png --edited t1_edit.png \
  --region <x0,y0,x1,y1> --out t1_v2.png
```

- `--region` の座標は coords.json（materialize出力）か画像目視から取る
- 出力の `changed OUTSIDE region: 0.0000%` を必ず確認
- **細部の修正は「切り出し→拡大編集→縮小して貼り戻し」が既定**: 全景カンプや
  タイル全体を渡して細部を直させると、小さい文字や細かい部品を描き切れない
  （実測: 全景のまま見出し修正→句読点欠けが2回連続）。直す範囲の周辺だけを
  切り出し、細かい文字・細部を含む場合は**2倍に拡大した状態で編集生成**し、
  元の大きさに縮小してから領域合成で貼り戻す。1発で通りやすく、生成範囲が
  狭いぶん安い（実測: 全景編集2回失敗$0.033 → 拡大編集1回成功$0.008）。
  写真の差し替えなど大きな要素は等倍のままでよい
- **横断スタイル統一（複数タイルの色・トーンがバラバラな時）**: 各タイルを
  1枚ずつ「配色だけを次の色に塗り替える」プロンプトで再生成する。**色は必ず
  明示hexで指定**する（背景#…・文字#…・アクセント#…。基準タイルから実測するか
  ユーザーに確定してもらう）。「この画像の色に合わせて」のような曖昧参照は
  **寄らないことが実測済み**（2026-08-18: 曖昧指定=色距離166→180で不収束、
  明示hex=指定色との距離5で正確に追従、レイアウト・文言・写真は完全保持）。
  塗り替え後は文字QAをやり直す
- レイアウト自体を変える修正（要素の追加・移動）は合成不可。タイルごと作り直し、
  文字QAをやり直す
- 貼った矩形が薄い帯として見えることがある。生成側の背景トーンが元と2〜4階調
  ずれるためで、広いベタ面だと段差になる。枠のすぐ内側のリングで色差の中央値を
  取って貼る側に足すと消える（実測 段差 2〜4 → 0.4）

> プロンプトは必ず**標準入力**で渡す（コマンド引数に改行入り文字列を渡すと
> フラグが壊れる事故の元。`gpt_image.py` はそのための設計）。
> `--mask` で修正領域をマスク指定することもできるが、モデルはマスク形状に
> 完全には従わないため、**領域外不変の保証は従来どおりこの手順の合成で行う**。

## Higgsfield fallback（OpenAI APIが使えない時のみ）

同じ GPT Image 2 を higgsfield CLI 経由でも生成できる:
`cat p.txt | higgsfield generate create gpt_image_2 --aspect_ratio 9:16 --resolution 2k --quality low --wait --json`
⚠️ プロンプトは必ず標準入力（`--prompt` 引数は改行でフラグが壊れる）。
`result_url` は明示的に読む（再帰URL探索は入力画像を掴む）。
