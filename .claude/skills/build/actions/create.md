# 制作の流れ

人間は「作って」と言うだけ。要件整理 → 実装 → 実物確認 → 納品 を自分で回す。
途中確認は方式で結果が大きく変わる分岐だけ。他は自分で決めて完成後にフィードバックを受ける。

---

## 1. 要件の整理

- 何を作るか（ダッシュボード / HP / LP / 機能ページ）、誰が使うか、必要な機能
- ユーザー提供の素材（写真・ロゴ・文言・参考URL・参考画像）を最優先で集めて把握する
- 媒体（スマホ縦の LP か、PC 中心の管理画面か）を先に決める
- 設計の連鎖（SKILL.md 2-3）で「何を見せれば行動に至るか」を一度整理する。書き出すかは任意

## 2. 方式・技法を決める

SKILL.md 2-2 の表から選ぶ。迷う時は軽い方式で作って見せ、ユーザーの反応で決める。
方式で結果が大きく変わる時だけ、平易な 2〜3 択を推奨つきで提示してから着手する。

## 3. 実装

- 新規 slug: `python scripts/editable_artifact.py init --slug <slug> --title "…"`
  → `frontend/src/app/artifacts/<slug>/page-body.tsx` に実装（SKILL.md 1-1）
- 編集対象に `EditableText` / `EditableElement`（1-2）。ヒーロー媒体は媒体側 CSS（1-3）。
  ゲートは `useSetupGate`（1-4）
- 部品（2-1）は合えば使う。合わなければ書く
- ダッシュボードで機能を伴う場合は DB → API → UI → 統合確認の順が整理しやすい
- ダッシュボードは `artifacts/<slug>/`（ダン管理画面内なら該当ページ）。
  試行錯誤は `scratch/<name>` か `demo/<id>`

## 4. 実物確認（`criteria.md`）

1. `python scripts/editable_artifact.py audit --slug <slug> --origin http://localhost:3001`
   で 3 幅スクショと構造検査（`scratch/editable-artifacts/<slug>/` に出る）
2. スクショを自分の目で見る。読みやすさ・切れ方・横溢れ・順序と密度。比較元があれば並べる
3. 手動編集ONで長文・改行・画像差し替え・余白変更 → 再読み込みで保存確認
4. 機能があれば curl と操作一巡と 3 状態
5. 欠陥は直して 1 に戻る。直せないもの・判断が分かれるものは理由を添えて報告に回す

構造検査の合格は見た目の保証ではない。画像内の残存文字、隠れた文字、写真の不自然な
切れ方は必ずスクリーンショットで確認する。

## 5. 納品

- `python scripts/editable_artifact.py finish --slug <slug> --review-notes "…"`
  （DAN のチャット実行環境では `--register` を付けて登録・配信経路に渡す）
- 公開URL（`share_url`）を curl かブラウザで確認
- 報告: スクショ添付、導線（どこから辿れるか）、品質・編集・保存・公開の検証結果を分けて書く。
  直せなかった点と理由。モックした保存テストを本番の証拠にしない

## 既存成果物の修正

- `release.gen.json` を先に見る（公開済み編集は JSX 上書きで反映されない。SKILL.md 1-2）
- 安定 ID と release を維持する。`init` を再実行しない
- 指摘された箇所だけ直す。他の要素の文言・分類を巻き込まない
- 画像ファースト方式で作られた既存 LP の部分修正は `recipes/image-first-lp.md` の修正ルーティング
