# デザイン成果物の作成（自己評価ループ内蔵）

このアクションは「生成→評価→改善」のループをスキル内で閉じる。
人間は「作って」と言うだけ。品質が基準を満たすまでダンが自律的に改善する。

> ⚠️ 自動学習 (learned.md への自動追記) は廃止しました。`criteria.md` の品質基準は
> 静的に固定されています。評価で見つけた知見を恒久ルール化したい場合は
> SKILL.md に明示的に追記してください (隠れ状態を作らない方針)。

## 手順

### Step 0: 用途の特定

成果物の種類を判定する:
- **A. ダッシュボード/管理画面** → Next.js + shadcn/ui
- **B. クライアントHP/ツール** → Next.js + shadcn/ui + Tailwind

(C. 提案書 HTML はユーザーが「提案書作って」と明示要求した時のみ `actions/proposal_html.md` を参照)

用途によって適用する `criteria.md` のセクション (A/B) が変わる。

### Step 1: 要件の整理

1. ユーザーの要件を整理する:
   - **何を作るか** (ダッシュボード / HP / ツール)
   - **誰が使うか** (自分用 / クライアント向け / 見込客向け)
   - **必要な機能** (KPI 表示 / フォーム / 決済 / CTA 等)
2. 不明点があればユーザーに確認する
3. **確認は最小限にする**。初回の指示で判断できる範囲は自分で決定し、完成後にフィードバックを受ける。途中で「A と B どちらがいいですか?」のような選択確認は原則しない

### Step 2: クリエイティブディレクション定義 (用途 B のみ)

HP制作の場合、コードを書く前に**ビジネスゴールからデザイン方針を逆算**する。SKILL.md Bの「ビジネスゴールからデザインへの因果連鎖」に従い:

1. **ビジネスゴール**: このHPで何を達成したいか
2. **訪問者の行動**: 訪問者に具体的に何をさせたいか（問い合わせ、予約、購入、資料請求…）
3. **訪問者の確信**: その行動をとるために訪問者が確信すべきことは何か（実績がある、美味しそう、価格が妥当…）
4. **必要なコンテンツ**: その確信を生むために見せるべき具体物（写真、数字、事例、地図…）
5. **デザイン方針**: そのコンテンツを最も効果的に見せるデザイン
   - 何が主役か（写真？テキスト？数字？）→ 主役を最も大きく目立たせるレイアウト
   - レンダリング方針: dom-first / comp-guided-dom / image-slice-hybrid / media-rich-hybrid
   - 表現パラメータ: visual_density / cta_intensity / motion_intensity / content_priority / authenticity_policy
   - 配色: 4層モデル（Neutral/Primary/Secondary/Accent）に従い仮決定
   - フォント: Headline/Body/Label を仮決定
6. 上記をプロジェクトフォルダに **`DESIGN.md`** として保存する

### Step 3: リファレンス収集 (用途 B のみ)

Step 2 で定義したクリエイティブディレクションに基づいてリファレンスを収集する。SKILL.md B「リファレンス駆動デザインプロセス」Phase 1 に従い:

1. ブラウザでユーザー提供URL、実在サイト、ギャラリーサイトを確認する (**DESIGN.md の方向性に合うもの**を探す)
2. ヒーロー・タイポグラフィ・配色・インタラクションを別々の参照元から収集
3. Reference Evidence / Interaction Evidence を DESIGN.md に残す。必要ならスクリーンショットもプロジェクトフォルダに保存する
4. SKILL.md B の方法 1/2/3 から最適な方法を選択

> **ユーザーが特定の参考サイト URL や画像を提供している場合、それを最優先のリファレンスとして使う。** 自分で Dribbble を漁る前に、提供されたものを WebFetch で開いてアスペクトを把握する。提供素材 (画像・動画・ロゴ) は AI 生成で代替せず実際に組み込む。

### Step 4: 初版生成

1. SKILL.md の用途別ルールに従う
2. **用途 B では Step 2 の DESIGN.md + Step 3 のリファレンスをインプットとして使う**。ゼロからデザインを想像しない
3. criteria.md の該当用途の品質基準を意識して、初版から高スコアを狙う
4. **A/B の場合はバックエンドファーストで実装する**: DB 設計 → API 実装 → UI 実装の順。UI を先に作らない
5. 用途に応じた場所に保存する:
   - ダッシュボード → `frontend/src/app/demo/` 配下
   - クライアント HP → `frontend/src/app/artifacts/{slug}/` 配下

### Step 5: 自己評価ループ (最大 3 回)

以下を最大 3 回繰り返す。1 回目は必ず実行する。

#### 5a. 視覚確認

- browser ツールで成果物を開く (ダッシュボード → localhost:3000、HP → dev server)
- スクリーンショットを取得する

#### 5b. 必須基準チェック (criteria.md の M 系基準)

- 該当用途の M 系基準を 1 つずつ確認する
- **1 つでも Fail なら即修正** して 5a に戻る

#### 5c. 機能確認 (A/B 共通)

1. 作成した API エンドポイントに curl して正常レスポンスを確認する
2. ブラウザで一連の操作 (作成 → 表示 → 編集 → 削除等) を実行する
3. ローディング中・エラー時・データ空の 3 状態が実装されているか確認する
4. **動かない機能があれば即修正** して 5a に戻る

#### 5d. 品質スコアリング (criteria.md の Q 系 + F 系基準)

1. **根拠 → スコアの順**で書く。先にスコアを決めない
2. スクリーンショットを見ながら具体的に述べる
3. A/B の場合は F 系 (機能基準) も採点する
4. 迷ったら低い方のスコアをつける
5. 「この評価で見落としている点はないか?」を最後に自問する

> ユーザーが特定の参考サイト URL や画像を提供している場合、生成物と並べて
> アスペクト類似度をここで確認する。提供素材を実際に組み込んでいるかも確認する。

#### 5e. 合否判定

- **合格条件**: M 系全 Pass + Q 系・F 系合算で平均 3.5 以上 + スコア 2 以下が 0 個
- **合格** → Step 6 へ
- **不合格** → 5f へ

#### 5f. 改善

1. 最もスコアが低い項目を特定する
2. criteria.md のスコア表で +1 に必要なことを確認する
3. 修正してファイル保存
4. → 5a に戻る

#### ループ上限に達した場合

- その時点のスコアと改善履歴をユーザーに報告する
- 現時点の成果物は出力する (破棄しない)

### Step 6: 出力

用途に応じた方法で出力する:
- ダッシュボード → 「ダッシュボードを更新しました」+ スクリーンショット添付
- クライアント HP → デプロイ URL or ローカルプレビューのスクリーンショット

## フロー図

```
用途特定 → 要件整理
              ↓
   [用途B] クリエイティブディレクション定義 (DESIGN.md)
              ↓
   [用途B] リファレンス収集 (ユーザー提供あれば最優先)
              ↓
        初版生成
              ↓
    ┌─ 視覚確認 (screenshot)
    │   ↓
ループ  │  M 系チェック → Fail → 修正 → ↑
(3 回) │   ↓ Pass
    │  Q 系採点 + リファレンス類似度確認
    │   ↓
    │  合格? ─ No → 最低項目を改善 → ↑
    └── Yes
              ↓
        成果物出力 + スコア報告
```
