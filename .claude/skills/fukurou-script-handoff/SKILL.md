# ふくろうPの台本修正と受け渡し

[ふくろうPの顧客対応・案件進行](../fukurou-client-operations/SKILL.md)のうち、台本文書を扱う部分。受付・面談・契約・請求は親スキルを使う。

お客さんが迷わず確認・編集・撮影できる文書を渡し、本人とダンの内部のやり取りは外に出さない。依頼された段階まで進める。「送れる状態にして」は準備の依頼で、送信の許可ではない。

## 修正中

- 現在の文書、本人のコメントと提案、会話で承認された内容を読む。ダンも提案モードで直す。本人の提案は、学習が済んだ後に学習の仕事が承認する（[talk-script/learning.md](../talk-script/learning.md)）。それ以外で勝手に承認・拒否せず、コメントを消さない。本文だけでなく画像の差し替えも提案として扱い、実際にその状態で入ったか確かめる。
- 本文を変えたら、内容に依存するタイトル・サムネ・選定理由・送信案もそろえる。完成済みなのに送信案が「できたら送ります」のままにならないようにする。本人が直した文面は保つ。
- 執筆・構成・サムネの判断が必要な時は [talk-script](../talk-script/SKILL.md) と該当資料を使う。このスキルで別の台本の型は作らない。

## お客さんに渡す文書

- タイトル、実際のサムネ画像、短い選定理由（2文まで）、台本を載せる。案が複数ならタイトルと画像の対応が分かる形にする。見出しと撮影指示の書式はtalk-scriptに従う。
- 内部向けの「前提と狙い」、制作上の検討メモ、LINE・メール等の送信文は入れない。送信文は顧客管理の該当する相手の下書きなど、こちら側で管理する。
- 特定案件の題材、豪華な背景など、その案件だけの指定を他のお客さんの既定にしない。

## 作業用とお客さん用の2本（2026-11-05 本人承認）

台本は2本に分ける。作業用は本人とダンだけが使い、本人のコメント・提案・ダンの提案が入る。お客さんには共有しない（共有先が本人とダンのアカウントだけか、渡す前に確かめる）。お客さん用は案件ごとに1本だけで、同じリンクを渡し続ける。

- お客さん用を作る・更新する時は `/Users/mikihonda/dan-venv/bin/python /Users/mikihonda/done/scripts/gdoc_client.py deliver --work <作業用ID> [--client <お客さん用ID>] [--name <初回の名前>]` を使う。作業用の確定した本文（未承認の提案は入れない）からコメントを除いて写す。2回目からは、前回渡した版から変わった所が「株式会社パイナ」の提案として見えるので、お客さんは提案モードと同じ見え方で変更点を確かめられる。
- 作業用に未承認の提案が残っていると止まる。本人が確定を認めた範囲だけ承認してから渡す。確定した部分だけ先に渡す時は `--allow-pending`（未承認の提案は入らない）。
- 前回渡した後にお客さんが直した・提案した・コメントした所があると止まる。`status --client <ID>` で中身を見て、作業用に取り込み（本人に要る判断は伝える）、それから `--force` で渡す。上書きするとお客さんの直しは消えるので、取り込まずに `--force` しない。
- この仕組みより前に渡したお客さん用の写しがある時は、新しく作らず `adopt --work <作業用ID> --client <その写しのID>` で引き継ぐ（今お客さんに見えている中身から変わった所が、次の deliver で提案になる）。
- お客さん用の ID と作業用の ID は案件の記録に残す。初回の共有範囲・通知の送信は下の「確定・受け渡し」に従う。

## 確定・受け渡し

- 本人が確定を認めた範囲の提案だけ反映する。未承認の提案が残る時は勝手に全承認せず、確定できる部分の準備を進め、残る判断を短く示す。既に得た承認は聞き直さない。
- 内部コメントは強い口調やお客さんに見せない内容を含む。単に「解決済み」にしても履歴で読める可能性があるので、それだけで除去済みとしない。コメントや提案を引き継がないお客さん用（上の `gdoc_client.py`）を基本にし、本文・画像・書式と承認された修正がそろっているか確認する。既にきれいな納品用文書があるなら不要なコピーを増やさない。
- 納品用は相手が編集できる権限にする。案件で決まった相手・共有範囲を使い、未指定なら相手を指定した共有を優先する。編集可という希望だけで「リンクを知っている全員」に広げない。通知による送信も、送信の許可がある時に行う。
- 受け渡し時点へ戻せる控えを内部に残す。確定済みの内部原本が同じ本文・画像を保持していればそれを使い、なければ非共有コピーを作る。元文書と控えのURL、確定時点を案件に記録する。版の履歴があるという推測だけで「必ず復元できる」と約束しない。
- 実際の納品用文書を開き、タイトルと画像、本文、内部コメント・未処理提案が残っていないこと、編集権限、控えを確認する。共有設定の表示と相手としての閲覧・編集確認は区別する。
- 送信案のリンクを納品用URLにそろえる。依頼内容と現在の段階に合う文章にする。送信の許可があれば最新の承認済み文面で送り、準備だけの依頼なら下書きで止める。

返事は納品用リンクと、送信済みか下書きか、本人に残る判断だけを簡潔に伝える。
