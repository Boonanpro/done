# 観察チェックリスト: 学び + メタ認知

会話の一区切り後に自動で呼ばれる。直前の会話を振り返り、学びがあれば記録せよ。
該当なしなら何も返答せず終了。（「学びなし」「変更なし」等の返答も不要）

---

## Part 1: 会話からの学び

以下のカテゴリに該当するFB（フィードバック）があるか確認する。

### 記録するかの判断基準

**記録する**: 実際にやらかした＋再発しそうなもの
**記録しない**: Claudeの一般知識で防げるもの、既にCLAUDE.mdに書いてあるもの、コードで対策済みのもの

### デザイン・HTML・UI（提案書・HP・ダッシュボード）
- ユーザーがHTML/UIの品質についてFBした箇所はあるか
- HTMLの修正を複数回やり直した場合、最終的に何が正解だったか
- → 記録先: `.claude/skills/design/learned.md` の該当セクション（A/B/C）

### 動画制作
- 動画の品質・制作プロセスについてFBがあるか
- → 記録先: `.claude/skills/studio/learned.md`

### ユーザーの好み・振る舞い
- ダンの振る舞いに対する修正指示はあるか（「短くしろ」「聞くな」「勝手にやるな」等）
- ユーザーが選んだ選択肢から暗黙の好みが読み取れるか
- → 記録先: `~/.dan/workspace/RULES.md`

### 作業の進め方
- 作業プロセス自体へのFBはあるか（「先に確認しろ」「テストしてから報告しろ」等）
- → 記録先: `~/.dan/workspace/RULES.md`

### 上記スキルに該当しない能力へのFB
- スキルが存在しない能力（経費処理、その他）へのFBがあるか
- → 記録先: `~/.dan/workspace/RULES.md`（スキルが作られたら移行する前提）

## Part 2: メタ認知（環境診断）

会話からの学びだけでなく、**なぜその問題が起きたか**をコードとログの両面から診断する。

### 手順

1. 今回の会話の room_id を確認する
2. 以下のコマンドでこの会話に関するエラーログを抽出する:
   ```
   grep "[room_idの先頭8文字]" D:/done/cli_runner_debug.log | grep -i "error\|Safety net\|exit code\|stderr\|failed"
   ```
3. 以下のパターンがあれば原因を分析して対策を記録する:

| パターン | 意味 | 確認すべきこと |
|---------|------|--------------|
| `Safety net: CLI exited without result` | CLIが結果を返さず死んだ | exit codeは何か。3221226505ならメモリ不足 |
| `exit code 3221226505` | Bunヒープ上限(4GB)超過 | Bashで重い処理を直接実行していないか。MCPツールに切り替えるべき |
| `exit code 1` + `MCP config file not found` | MCP設定の競合 | タイミング問題。再実行で解消するか |
| `prompt is too long` | セッション履歴の肥大化 | セッションを分割すべき |
| `malloc.*failed` | 子プロセスのメモリ確保失敗 | ffmpeg等をMCPツール経由にすべき |

4. **ログだけで完結しない。** エラーの根本原因を特定するために、関連するソースコード（`app/agent/`, `app/tools/`, `app/api/` 等）を読んで以下を確認する:
   - そのエラーが発生するコードパスはどこか
   - 既に対策済みのコードがあるか（try/catch、リトライ、フォールバック等）
   - 対策済みなら記録不要。未対策の場合のみ記録する
5. ユーザーのFBとログを突き合わせる。「ユーザーが怒った理由」がログのエラーで説明できる場合、学びとして「原因→対策」をセットで記録する。

### 記録先
- designスキル関連 → `.claude/skills/design/learned.md`
- studioスキル関連 → `.claude/skills/studio/learned.md`
- その他のスキル関連 → 該当スキルの `learned.md`（なければスキルディレクトリに作成）
- 全体的な運用ルール → `~/.dan/workspace/RULES.md`

## 記録のルール

### 品質基準（これを満たさない学びは記録しない）

1. **具体的なアクションがあること。** 「注意する」「気をつける」は記録しない。「Xの場合はYする」の形にできないなら記録に値しない。
2. **コードで検証済みであること。** エラーに対する学びは、ソースコードを読んで原因を特定してから記録する。ログの表面的なメッセージだけで推測したルールは記録しない。
3. **既存の対策と重複しないこと。** コードに既に対策が実装されている問題を「ルール」として記録しない。
4. **Claudeの一般知識で防げるものは記録しない。** Next.jsの基本的な仕様、一般的なプログラミング知識などは記録不要。実際に何度もやらかして再発リスクが高いものだけ記録する。

### 記録の作法

1. **まず記録先ファイルを読む。** フォーマットと既存内容を把握してから編集する。
2. **追記・更新・削除を行ってよい。**
   - 新規の学びがあれば → 既存フォーマットに合わせて追記する
   - 同じ内容が既にあれば → 確認回数を+1するだけ（重複追記しない）
   - 既存のルールが陳腐化していれば → 削除または更新する
3. **学びは「汎用的な原則」として記録する。** 特定のプロジェクト名やセクション名だけに依存する記録にしない。ただし、その原則が生まれた具体的な場面も1行で添える。
4. **過剰に記録しない。** 明確な学びだけを記録する。曖昧なものは無視してよい。
5. **RULES.md への記載は簡潔に。** 1-2行で済むルールとして書く。
6. **ルールには前提条件を併記する。** 記録時に `（前提: ○○）` を添える。前提が崩れたらそのルールは削除対象。

### 陳腐化の判断基準

既存ルールを読んだ際、以下に該当するものは削除または更新する:

- **前提条件が崩れている**: コードを確認して、ルールの前提となる構造・実装が既に変わっている
- **コードで対策済み**: ルールが警告している問題が、コードレベルで既に解決されている
- **アクションが曖昧**: 「注意する」「気をつける」等、具体的な行動指針がないルール
- **重複**: 同じ内容が別の箇所（CLAUDE.md、スキル定義等）に既に書かれている
